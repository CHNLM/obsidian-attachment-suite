## 四个容易踩的点

1. **别用"用例数"推断覆盖**。验收用例数（82）衡量的是**输入形态多样性**，不是功能分支矩阵；
   真正的判据在 `coverage-audit` 的矩阵里。
2. **别凭文件时间戳判断内容时效**。本目录多篇文档在改动**之后**被追加过章节（如
   `real-host-run` 的 §10/§11、`coverage-audit` 的 §9–§14），时间戳不等于全文写于该日。
3. **当前规模只允许有一个权威来源**：`Attachment Suite/tests/README.md` 第 8 行。别的文档**不要再复制一份数字**——
   复制即漂移（2026-10-02 就是这么落后的：加了 11 个用例只同步了一处，`coverage-audit`
   的「规模」小节停在两个版本之前）。若确需在「规模」小节里再声明一次，必须与它**逐字一致**——
   `tests/unit/docs-consistency.test.ts` 会对账；历史轮次的数字请放进「历史归档」区或带明确时间限定。

4. **只有一条链路：校验是发布的前置**。`.github/workflows/release.yml` 是仓库**唯一的自动化入口**
   （推送版本标签或手动触发），它按 `detect-version → verify → build-release` 串联：先做前置校验，
   再跑 `.github/workflows/verify.yml` 的 typecheck / test / build（ubuntu + windows 各一遍），
   **校验通过才**构建、签名并创建 Release。推 `main` 与 PR **不会**触发任何校验或构建——
   ⚠️ 所以**不要**给默认分支加"要求状态检查通过"的保护规则：那些检查不再在 PR 上运行，
   加了会让所有 PR 永久卡在"等待状态上报"。职责与权限的划分见 [`invariants.md`](invariants.md) §6。
   （手动触发时可选 `dry_run`：跑完校验与构建，但跳过签名与建 Release——验证链路不必真发一版。）

> 上述四条中，**第 2、3 条与"当前有效文档清单"已由 `docs-consistency.test.ts` 机械看守**——
> 它还校验本目录文档里引用的**文件与符号是否仍然存在**（防重构后引用失效）；第 4 条涉及的工作流
> 由仓库自身在运行时把关。该守卫正是读**本文件的索引表**来确定"哪些文档算当前有效"，
> 所以新增文档时把它们登记进上表，就等于把它们纳入了自动对账。
