## 1. 三层覆盖结构（先说清"哪一层验了什么"）

| 层 | 载体 | 验的是 | 盲区性质 |
|---|---|---|---|
| 单元 | `tests/unit/**` | 纯逻辑（命名、解析、相似度、路径规则…） | 不接触 Obsidian，发现不了"与宿主交互"的问题 |
| harness E2E | `tests/e2e/**`（替身 `infrastructure.ts`） | 命令行为、设置页、通知契约、落盘位置 | **替身可能比真实宿主更宽松或更强**（已 5 次踩中） |
| 真实宿主 | `scripts/obsidian-cdp-acceptance.mjs`（6 个 `--variant` + 2 个正交参数） | 13 条命令 × 收敛轮次、引用形态、幂等、启动哨兵；**另含报告内容与定位、设置页渲染、通知三档、schema 迁移、能力门禁、网络策略探针** | 仍**比 harness 窄**：纯逻辑分支与"输入形态"矩阵只在单测/harness 覆盖。⚠️ 但"脚本不读界面"是**过时说法**——它现在会读报告窗文本（`.iap-report-modal`）与页面通知（`.notice-container`），并断言提示内容 |

**关键认知**：真实宿主那一层是"最终防线"，但**它不替代前两层**——
harness 负责分支矩阵，真实宿主负责"替身骗了我们"的那一类。

## 3. 专题：启动门与批量护栏（唯一一条"不经同意就批量改写整库"的路径）

插件启动时，Obsidian 会对**全库笔记**批量触发 `metadataCache.changed`。若不区分，它们会被当成
"用户编辑了这篇笔记" → 全部标脏 → 下一轮轮询逐篇自动处理（内部 `confirm=false`）→
**用户只是打开了 Obsidian，整个库的附件就被改名搬走**。

两道防线（判定在 `src/features/automation-core.ts`，纯函数、可单测）：

| # | 防线 | 判据 |
|---|---|---|
| ① | **条件式就绪门** | `metadataCache.resolved` 之后再过余震窗口；时长随库自适应，替代"固定 1500ms"这类在大库上会失效的启发式 |
| ② | **批量护栏（fail closed）** | 单次轮询待处理笔记数超过上限即**整批拒绝**并明确告知（用 error 级，静默档也可见） |

- **兜底放行**：宿主不发就绪事件时，超时后按已就绪处理并记 warn——它**只影响可用性，不影响安全性**。
- **可取证**：`getAutomationDiagnostics()` 暴露"挡下多少个 changed / 就绪信号来源 / 护栏拒绝次数"。
- **非空洞证据**：真实宿主 `--startup-check` 实测——完整实现下 **笔记改写 0 篇、哨兵附件完好**，
  而就绪门**真的挡下了数十个**启动期 changed；把两道防线都关掉能**复现**批量改写。详见
  [`../records/real-host-log.md`](../records/real-host-log.md)。

## 4. 设置项覆盖：一套配置 vs 默认值

真实宿主只用**一套** `ACCEPTANCE_SETTINGS`，与默认值不同的是十余处（多为网络与正文扫描相关，
**功能开关类几乎全是默认值**）。因此下面这些**非默认分支**只在 harness 里被覆盖：

| 设置 | 非默认分支的真实宿主覆盖 |
|---|---|
| `naming.folderByCategory` / `addTime` / `addPathHash` / `showSubType` | ✅ `--variant naming-rich`（四个一起开）实测：附件真的落进 `notes/assets/<类别>/`，`image` / `video` / `audio` / `pdf` 四个类别子目录在多个笔记目录下都被建立，文件名含「类别_扩展名_序号_时间戳_哈希」且引用随落盘一起改写。**这一格第一次打开就抓到两个真缺陷**（`parseRenamed` 幂等、收集与重命名目标目录不一致），均已修——见 §5「本轮已闭环」 |
| 四个能力总开关 | ✅ `--variant abilities-off`（2026-10-18）：命名/本地化/一致性/清理/导出 + 自动化全关 → **11 条受门禁的命令逐条早退并明说「X 能力已关闭」、无一弹窗**，全程 `71 → 71 → 71`（**库零变化**）、第 2 轮收敛、问题 0；同时断言真孤儿仍在、回收站不增、外链未改写、可修断链原样保留 |
| `localize.blockPrivateHosts` | ✅ `--variant net-strict`（2026-10-18）改为 `true`：`127.0.0.1` 因**在白名单里**被放行（这正是 `allow` 覆盖 `private` 的实证），非白名单的 `.invalid` 被拦。基线（`false`）下走的是"连不上 → 保留原文" |
| `localize.hostAllowlistOnly` / `minSizeKb` / `maxDownloadMb` / `perHostIntervalMs` | ✅ `--variant net-strict`（2026-10-18）：`blockPrivateHosts=true` + `hostAllowlistOnly=true` + `allowHosts=['127.0.0.1']` + `maxDownloadMb=50` + `perHostIntervalMs=20`，问题 0。两条探针断言：**白名单域仍被下载**（`allow` 在 `private` 之前，否则整个夹具的外链都会被拦）、**非白名单域在发请求前被拦**且摘要归入「名单」。⚠️ **`minSizeKb` 仍是默认 0**——夹具文件只有十几字节，任何正阈值都会把它们全部跳过（测到的是"过滤生效"，代价是主流程失去全部下载样本）；该轴由 `localize-media-core` 单测覆盖 |
| `consistency.platforms` | ⚠ 只用 `['windows']` |
| `consistency.followNoteMove` | ✅ 两条分支都验过：`true`（`custom` / `naming-rich`：独占探针 → 笔记搬走、附件跟随、旧目录清空，2026-10-18）与 `false`（`--variant follow-off`：笔记搬走、**附件原地不动**，2026-10-18）。⚠️ **库根落盘模式（`obsidian-root`）下这条能力按设计是空操作**，探针在该变体显式跳过（附件本就不在笔记相对目录里，硬跑只会得到假红） |
| **落盘位置**：`attachmentFolderMode='obsidian'` + 库根 | ✅ `--variant obsidian-root` 实测附件落**库根**、无 `notes/assets` |

> 脚本靠"包装 `window.Notice`"采集通知，但**插件在加载时就绑定了它自己的 `Notice` 引用**，事后包装

> "报告 `notices` 为 0"排除"引用改写抛错"——该依据**不成立**（当时结论另有直接证据：查库确认引用

>

> 去跑另两条**不可逆**路径。**强断言**：非默认模式下库内回收站必须**全程为空**（走系统回收站或
> 永久删除的，库内不该留痕）；**防空转**：同时断言夹具的真孤儿（O01/O02）**确已从库内消失**，
> 否则"回收站为空"是空洞的绿。
> **实测**：`system-trash` 与 `permanent` 均 **问题 0**、**库内回收站累计 0 项**、终态文件数 **94**
> （与默认模式一致）；逐命令追踪里 `cleanup-unused` 的变化项是 **`-assets/…`**（从库内消失），
> 而默认模式下同一命令出现 **`+.trash/…`**——两条路径确实不同，接线正确。
> **一并澄清**：非默认模式"收敛要 4 轮"**与删除模式无关**——同一次对照里默认模式也是 4 轮
> （`71→92→93→94→94`）；轮数取决于**外链本地化的时序**（下载快 3 轮、慢 4 轮），不是删除去向的产物。
>
> **2026-10-16：收敛判定"看不见轮内创建 → 销毁"的盲区已闭合**（原 §5 最后一格）。
> 判定原先只比较**轮末**快照：某附件若每轮"建一份、删一份"，轮末快照恒定 → 判为收敛（**假绿**）。
> **修法**：把**库内回收站的新增项**并入每轮的变化集合——附件被删必然落到那里，且**轮末可查、
> 零额外开销**。判据取**插件自己的** `cleanup.deleteMode`（`unused-cleaner` 据此决定删到哪），

## 6. 一句话方法论

**"用例数"不等于"覆盖度"。** 验收用例回答的是"各种输入形态下库会不会被改坏"，
而不是"每个功能分支是否按预期工作"。两者都要，但**判断缺口必须按"能力 × 分支"去看**——
历史上最危险的三处缺口（两种删除模式、默认落盘模式、自动化）在用例集里各有"看着像"的邻近用例，
实际上从未执行。
