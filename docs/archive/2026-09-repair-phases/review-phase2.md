## 2. 新增：安全专项套件（`tests/e2e/safety-suite.test.ts`，8 条）

### 2.1 引用形态 ↔ "在用"保护 覆盖矩阵（全部已断言）

| 引用形态 | 是否纳入"在用"保护 | 实现依据 |
|---|---|---|
| 正文 markdown 图 `![](assets/a.png)` | ✅ | `usedByBasename`（原始文本） |
| 正文 wiki 嵌入 `![[assets/a.png]]` | ✅ | 同上 |
| 短名嵌入 `![[a.png]]` | ✅ | 同上（basename 唯一时还会合成引用） |
| **无扩展名短名** `![[a]]` | ✅（本次修复） | `stemPaths` 反查 |
| **URL 编码** `![](assets/enc%20oded.png)` | ✅（本次修复） | 原始 + 解码双写法 |
| frontmatter `cover: assets/a.png` | ✅ | `managedBasenamesFromFrontmatter` |
| canvas `file: assets/a.png` | ✅ | `canvasFileRefs` |
| HTML `<img src="assets/a.png">` | ✅ | `listMatches` 覆盖 HTML 标签 |

### 2.2 其他安全断言

- 排除目录（全局 `paths.exclude`）内的未用附件不被清理；
- **断链修复不得把引用改到不存在的目标**（若发生改写，必须断言目标真实存在）；
- 多个同名候选 → 不得自动改写（必须由用户选择）；
- 无任何候选 → **用全文比对**证明零改动；
- 幂等：全库命名跑两遍文件名集合完全一致、且不产生 `(1)` 兜底名；清理未用跑两遍第二遍零删除；断链修复跑两遍零改动。

## 3. 测试基础设施发现（影响结论可信度，需记录）

**测试替身的链接解析比真实 Obsidian 宽松**：`tests/e2e/infrastructure.ts` 的 `metadataCache.resolvedLinks` 按 **basename** 解析，因此 `![x](nowhere/uniq.png)` 在替身里会被判为"已解析"（`status: resolved`），而真实 Obsidian 对 **markdown 路径式链接**是按路径解析的 → 该引用在真实环境里是断链。

- 影响：E2E 对"断链检测/修复"的部分结论**可能偏乐观**（漏报被掩盖）。因此本次安全套件对这一类断言只校验"**绝不改到不存在的目标**"这一不变式，而不是断言"一定会被自动修复"。
- 处置：不修改替身（改动风险大且会牵动既有断言），改由**三阶段真实 Obsidian 验收**覆盖此类场景——验收库中已含"路径不符但存在同名候选"的断链用例。

### 7.1 规模基线（首次量化，`tests/e2e/scale.test.ts`）

| 指标 | 200 条目 / 60 笔记 / 180 附件 |
|---|---|
| `index.build()` | **36–58ms** |
| 一致性审计（全量扫描 + 报告） | **30–46ms** |
| 全库命名第 1 遍（180 次真实改名） | **217–355ms** |
| 全库命名第 2 遍 | **12–15ms，且不弹预览（幂等）** |

> 观察（未构成缺陷）：`planBulkRename` 的规划是 `O(笔记数 × 条目数)`（`planForSnapshot` 每次遍历全部条目）。在 60×200 下无感；若库规模达到"数千笔记 × 数万附件"，规划阶段会走到千万级循环，建议三阶段用更大规模夹具复核（已记入待办）。

### 7.2 一次误判的排查记录（方法论留痕）

排查过程中出现过"全库命名第二遍耗时 **84 秒**"的表象。逐层定位（规划 20ms / 执行 83.6s / 缓存快照是最新的 / 直接调 `planBulkRename` 得 total=0）后确认：**是测试助手复用了上一轮的弹窗回调**——第二遍其实"无可重命名项、根本没弹窗"，助手却把上一轮遗留的确认回调又点了一次，于是拿着**过期快照**去改名**已不存在的文件**，每项白等 3 次退避。结论：**非插件缺陷**。

附带收益：把安全套件的幂等断言从"文件名集合不变"升级为更精确的 **"第二遍不得弹预览 / 不得弹确认"**；并顺手把三处单测替身里"源文件不存在"的不真实夹具改正。
