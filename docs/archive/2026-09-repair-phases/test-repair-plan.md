### 0.3 缺陷分级

| 等级 | 定义 | 处理 |
|---|---|---|
| **P0** | 数据丢失 / 误删 / 引用被改到**错误文件** / 破坏用户笔记 | 立即修 + 复现测试 + 报告置顶 |
| **P1** | 功能与声明不符、单篇↔全库语义不一致、门禁或排除目录漏生效、静默丢弃、失败留半成品 | 立即修 + 复现测试 |
| **P2** | 边界与体验：大库性能、内存峰值、长任务无反馈、极端文件名、错误提示误导 | 按最优方案修（含必要的语义/提示调整），逐条记录 |
| **P3** | 文档与实现不符、注释过期、命名不统一 | 直接修 |

### 0.4 作业规则（红线）

1. **不破坏分层**：`infra ← core ← features`；纯计算进 `*-core.ts`，执行留 `*.ts`。
2. **数据安全优先**：任何破坏性路径必须满足 `预览 → 确认 → 执行前复检 → Obsidian 安全 API → 无半成品 → 可恢复`。
3. **`for-test` 保护**：动手前备份；破坏性操作前先做快照（zip）；生成器可**重建**验收库（等价于可回滚），只写 `for-test/acceptance/` 与 `docs/`。
4. **每个修复先有复现测试**：先写能失败的测试，确认是真缺陷，再修。
5. **测试节奏**：一、二阶段只跑改动关联测试 + `typecheck`；**三阶段统一跑全量真实测试**（含 `npm test` 全量与真实 Obsidian）。发现新问题即时修，修完回到本阶段门禁。
6. **一切裁定留痕**：我自行决定的取舍（含语义/默认值/提示变更）写进阶段报告，供你回来复核。

## 2. 审查方法（六种手段）

1. **静态精读 + 依赖核验**：读完全部源码；核对分层、`*-core` 纯度、导出是否被误用。
2. **对称性 / 差异法**：单篇↔全库、文档↔代码、预览↔执行、预览↔实际计数。*（上一轮三处缺陷即出自此法）*
3. **对抗法**：最坏输入矩阵（脏名、断链、共享、同名、编码、超长、只读、并发、中断、空库）。
4. **动态复现**：每个怀疑点先写"能失败的测试"。
5. **安全链核验**：破坏性路径六环闭环检查。
6. **反向验证（本轮新增）**：对"看起来正确"的关键判定（如白名单闭合、索引排除、幂等）**用测试把结论钉死**，防止后续改动悄悄回归。

### 3.2 核查项 A1–A30（"为什么怀疑"为待验证假设）

**A. 本地化 `localize-note`**

| # | 怀疑点 | 为什么怀疑 |
|---|---|---|
| A1 | frontmatter 中的外链是否被本地化 | 断链检测层**明确覆盖** frontmatter，本地化改写路径却只走正文/HTML/wiki → 可能口径不一致 |
| A2 | 下载成功但 `vault.modify` 失败 → 已落盘文件成为无引用孤儿 | 代码顺序为"先写盘、后改写"，缺失败补偿与明确提示 |
| A3 | **落盘类别 ↔ 受管附件白名单不闭合** | `classify()` 放行 `document`（含 `.txt` 等），而 `isManagedAttachment()` 是按扩展名的白名单 → 文件能落盘却"没人管" |
| A4 | 被过滤的引用（体积/白名单/主机）**是否保持原样** | 过滤后若能留下空引用或坏链接即为 P0 |
| A5 | 同一 URL 多次出现（不同 alt / 不同语法）改写是否各保其形 | `uniqueByUrl` 去重 + `map` 回填，需验证不串味 |
| A6 | `useMarkdownLinks` 读取失败/为真时的输出形式与回退 | 依赖 vault 配置，回退路径需确定 |
| A7 | `data:` 与 `http` 混排、`data:` 解码失败的处理 | 已有预判逻辑，需端到端验证 |
| A8 | 排除目录判定用的是**笔记路径**；那么"笔记在根、附件目录在排除目录内"呢 | 排除语义只作用于笔记，附件落点可能落到排除目录（与清理语义冲突） |
| A9 | `minSizeKb` 下限丢弃时的提示与计数 | 静默丢弃会让用户以为"没触发" |
| A10 | 本地化后"静默接续命名"与自动化 sweep 的竞争 | 两条写路径并发时的幂等兜底 |
| A11 | 下载落盘路径已存在但内容不同（同名不同内容） | `exists` 即跳过会保留错文件 |
| A12 | 备注名/目录含 `#`、`?`、`%` 时链接改写的正确性 | wiki 链接语义中 `#` 是锚点 |

> 合计 **≥ 74 条用例**，全部由生成器产出真实文件，并附 `EXPECTED.md`（每条预期结果，供人工与自动断言共用）。

### 5.3 执行步骤

1. **构建**：`npm run build` → `dist/attachment-suite/`（含 `main.js`/`manifest.json`/`styles.css`）。
2. **投放**：复制到 `for-test/acceptance/.obsidian/plugins/attachment-suite/`；写 `.obsidian/community-plugins.json`（启用插件）与 `data.json`（验收配置）；备份快照。
3. **自动化全量（harness 版）**：`tests/e2e/acceptance.test.ts` — 把验收库复制到临时库 → 依次执行全 13 命令（含自动化事件路径）→ 按 `EXPECTED.md` 断言 → **全命令跑第二遍**验幂等。
4. **真实 Obsidian 全量（CDP 版）**：以
   `Obsidian.exe "…\for-test\acceptance" --remote-debugging-port=9222`
   启动；经 CDP（Node 全局 `WebSocket`）连接渲染进程，执行：
   `await app.plugins.enablePlugin('attachment-suite')` → 逐条 `app.commands.executeCommandById('attachment:…')` → 自动点击确认/候选弹窗（读取 DOM 调用按钮 click）→ 采集 `Notice` 文案与最终文件树 → 与 `EXPECTED.md` 比对 → 再跑第二遍验幂等。
   - 失败回退：若 CDP 不可用（版本差异），改用"人工清单"模式：我给出逐命令操作步骤 + 预期 + 判据，你回来点一遍即可。
5. **问题修复循环**：发现问题 → 临时库复现 → 补复现测试 → 最小修复 → 关联测试 → 回 §5.3 重跑该命令。

## 6. 风险与应对

| 风险 | 应对 |
