## 3. harness 版全量验收（已完成）

一次执行即完成：生成用例库 → 执行 4 个「当前笔记级」命令 ×4 篇宿主笔记 → 执行全部 13 条命令 → 再跑一遍验幂等。

**断言策略改为"语义不变式"，而不是逐条写死最终路径。** 原因：一轮 13 命令会连锁改名/移动/改写引用，写死路径的断言会被"合法但不同于预期"的中间态大量误报，而且它并不能证明真正要紧的事。改为：

| # | 不变式 | 想挡住什么 |
|---|---|---|
| 1 | 非受管文件（`noext`/`txt`/`zip`/`csv`）不得被改名或删除 | 越权管理 |
| 2 | 排除目录内容与空目录整块不动 | 排除语义被穿透 |
| 3 | **每篇笔记"可解析引用数"不低于运行前** | 制造新断链（数据损坏） |
| 4 | 仅 canvas / 仅 frontmatter 引用的附件不得消失 | 保护层漏判 → 误删 |
| 5 | 所有被引用的附件必须真实存在 | 引用悬空 |
| 6 | 应本地化的笔记不再含测试服务地址 | 本地化漏做 |
| 7 | 保形改写（HTML 标签不得变成 `![](`；普通链接不得变成图片嵌入） | 语法破坏 |
| 8 | 命名生效（`01-正文图片_image_NNN.png`） | 命名漏做 |
| 9 | 真孤儿被清理 + 导出 zip 生成 | 命令真的执行了（避免"全都没跑"也判通过） |
| 10 | 空目录矩阵（3 个该清、1 个含隐藏文件不该清） | 空目录边界 |

### 3.1 本轮抓出的真实缺陷（P0，数据损失）

**引用路径含空格时被按空白截断 → 「清理未用附件」删除仍被引用的附件。**

- 现象：`notes/15-中文 空格 emoji 😀.md` 的引用在经历「收集 → 全库命名」后被写成
  `notes/assets/15-中文 空格 emoji 😀_pdf_001.pdf`；随后 `cleanup-unused` 把该文件**删掉**，笔记当场断链。
- 根因：`src/core/link-resolver.ts` 的 `MD_LINK = /!?\[([^\]]*)\]\(([^)\s]+)…/` —— 目标段
  `([^)\s]+)` **不允许空白**，于是上面的引用被读成 `notes/assets/15-中文`，扩展名丢失 →
  该引用不进"在用"集合 → 附件被判为孤儿。
- 触发面为什么很广：**"名字里带空格"正是插件自身命名功能最常产生的形态**
  （`<笔记名>_image_001.png`，笔记名常含空格）。也就是说，用户越是用好这个插件的命名功能，
  越容易在随后的一次「清理未用」中丢附件。
- 修复（`0bf4892`）：
  1. `listMatches` 改为整体捕获括号内容，再按 CommonMark 规则剥离 `<...>` 与 ` "标题"`；
     目标做 `%xx` 解码，使 `linkText` 与库内**字面路径**一致（否则含 `%20` 的引用既命不中
     "在用"集合，也命不中改名映射）。
  2. `replaceTargetInRaw` 改为重新拼装链接外壳，替新目标做 `encodeMdTarget`（空格→`%20`、
     圆括号→`%28/%29`）：裸空格在 CommonMark 里根本不是链接（会退化成纯文本），
     而 Obsidian 自己生成的也正是 `%20` 形态。
  3. 同函数改用**函数式替换**：新目标含 `$&`/`$1` 时不再被当作替换模式展开而改坏正文
     （与一阶段本地化模块同类问题的第二个实例）。
  4. frontmatter 资源 token 重写：首字符不允许空白与 `-`（否则 `cover: a.png`、`- a.png`
     会从分隔符起匹配、整段 trim 后匹配不上映射而漏改）；字符类改用 `\p{L}\p{N}`，
     顺带修好"中文附件名的 frontmatter 引用改名后必然悬空"（过去字符类只含 ASCII）。
  5. 本地化模块的 markdown 目标一并编码（同源加固）。
- 回归钉子：链解析单测 +6（空格/尖括号/标题/%20/编码写回/`$` 转义/frontmatter 空格与中文）；
  安全套件 +1（含空格与 `%20` 引用的附件不得被清理误删）。

> 这条与二阶段那两个误删（无扩展名短名、URL 编码引用）是**同一类病**：
> "保护层的口径比插件自己会写出的引用形态更窄"。二阶段补了两种形态，三阶段又补了空格与括号。
> 因此在本轮把"**插件自己写什么，保护层就必须认什么**"定为不变式，并用上面第 3 条断言长期看守。

### 3.2 测试基础设施的两处保真度问题（已修 / 已记）

1. **已修**：stub 的 `fileManager.renameFile` 原先只做文件移动，不做"改名后全库联动改写引用"，
   而真实 Obsidian 会做。这会让"改名导致其它笔记引用变坏"在 E2E 里变成**假阳性**。
   现改为复用插件的纯改写器（`rewrite` + `rewriteFrontmatter`）做同样的联动，与真实语义对齐。
2. **已记未修**：stub 的 `metadataCache.resolvedLinks` 按 basename 解析，比真实 Obsidian
   （markdown 路径式链接按路径解析）**宽松**，因此 E2E 对断链类的结论偏乐观。
   裁定不改替身（牵动大量既有断言），由真实 Obsidian 那一遍兜底。

### 3.3 一处我自己的配置坑（顺手变成加固）

最初把域名黑名单写成 `127.0.0.1:45999/deny.png`（**带路径**），而名单是按**主机名**匹配的 →
整台主机被拦，15 条外链全部"被拦截"，误导了一轮诊断。这暴露一个真实的易用性陷阱：
用户粘贴 URL 进名单时，`https://ads.example.com/x.png` 会被 `:` 截成 `https`（永不命中、静默失效），
`example.com:8080/x` 会被截成 `example.com`（整台主机被拦）。已在 `normalizePattern` 里收口
（去 scheme / 去路径 / 去 userinfo 后再取主机），并补单测。

### 4.2 只有真实宿主才暴露的四处差异（harness 永远测不到）

这三条是"用真实 Obsidian 再跑一遍"的全部价值所在——它们不在插件代码里，而在宿主行为里：

1. **命令 id 会被 Obsidian 加插件前缀。** 源码注册 `attachment:check-consistency`，真实 id 是
   `attachment-suite:attachment:check-consistency`。按源码 id 调 `executeCommandById` 会**静默返回 false**
   ——日志上看着"13 条命令全跑完、无弹窗"，实际一个文件都没动。脚本已改为**从运行中的实例按后缀动态解析 id**。
2. **Obsidian 原生「更新链接？」弹窗会打断批量改名。** 它由 `fileManager.renameFile` 弹出，
   触发条件是 Obsidian 设置里「自动更新内部链接」**关闭（默认值）**。后果两层：批量改名被逐个打断；
   用户若点「不做更新」，那次改名的引用改写就被搁置。脚本已识别该弹窗并点 `总是更新`（会被记住），
   验收库 `app.json` 也显式写入 `alwaysUpdateLinks: true`。
3. **库索引可能与磁盘不一致。** 验收库由"外部"（seed 生成器）整体重写，Obsidian 的文件监听跟不上
   批量删除时会留下**幽灵条目**（磁盘已无、索引还在）。此时整轮结论都建立在假数据上。
   脚本因此加了前置校验：`索引文件数 === 磁盘文件数`，不一致直接拒绝运行并提示执行
   「Reload app without saving」（`app:reload`）。
4. **一轮跑完不等于稳定。** 「收集（把附件搬到笔记归属目录）」在命令顺序里排在「重命名（原地改名）」
   之前，本轮命名出的文件要等下一轮的收集才进笔记目录；真实宿主的库缓存/索引在插件自身改写后也有轻微滞后。
   两者叠加使状态需要多轮才稳定。**幂等的正确表述是"有限轮内收敛"，不是"第一遍后就不再变化"**。
   （harness 版此前标题写了"再跑一遍验幂等"但实现里没跑第二遍，本轮一并补齐为"循环到收敛"。）

### 4.3 本轮由真实宿主抓出并修复的两个真缺陷

**① 只含点文件的目录被当空目录清理（已修）**

- 现象：D05 用例 `empty/hidden-file/.DS_Store` 所在的目录被移入回收站。
- 根因：判定"空目录"用的是 Obsidian 库索引（`getAllLoadedFiles`），而**索引不含点文件**
  → 只含 `.DS_Store` / `.gitkeep` 的目录在索引视角是空的。
- 影响：`.DS_Store` 删除无害；但 `.gitkeep` 是用户明确用来占位的文件，删掉目录等于动了用户圈起来要留的东西。
- 实测确认：真实 `adapter.list('__probe__')` 返回 `{files: ['__probe__/.DS_Store', ...]}`（**看得见点文件**），
  而 `getFiles()` 看不到。修复即"删除前回查真实文件系统"（`isReallyEmpty`），读不到内容时按**非空**处理，
  并如实报告"因实际含隐藏文件而保留 N 个"。
- 顺带修正了测试替身的保真度：`getFiles`/`getAllLoadedFiles` 隐藏点项（与 Obsidian 一致）、
  `adapter` 补上 `list`/`exists` 的文件系统视角。**此前替身把点文件当普通文件，正是它让这类缺陷在 E2E 里隐形。**

**② `resolvedLinks` 把 HTML 媒体标签引用"挤掉" → 共享误判为独占（已修）**

- 现象：`notes/18-HTML媒体标签.md` 的 `<audio src="assets/mp3/song.mp3">` 在附件被改名后悬空。
- 根因：`attachment-index` 的引用装配是**二选一**——只有当 `usedTargets`（来自 Obsidian 的
  `resolvedLinks`，**不认识 HTML 标签写法**）**为空**时，才用 `usedByBasename`（按正文文本扫出来、认得）
  去合成引用。于是"既被 markdown 链接引用、又被 HTML 标签引用"的附件会丢掉后者：
  - `clip.mp4`（只有 HTML 引用）→ resolvedLinks 无 → 合成 → 正确登记
  - `song.mp3`（markdown + HTML 两种引用）→ resolvedLinks 已有 markdown 那条 → **跳过合成** → HTML 引用丢失
- 影响链：共享判定误判为独占 → 「重命名全库」原地改名而非按笔记各复制副本 →
  HTML 那种 Obsidian 不认识、改名联动不会改的引用**当场悬空**。
- 修复：两套口径**合并**（按来源笔记去重），保留"basename 唯一才合成"这个安全前提。
- **这是第四次同源缺陷**（前三次：无扩展名短名、`%20`、含空格路径）。这次的"两层"是
  **Obsidian 的解析结果** 与 **插件自己的文本扫描**。

### 4.4 验收工具链因此增强

- 前置校验：索引与磁盘不一致 → 拒绝运行（防止结论建立在幽灵索引上）；
- **逐轮**跑不变式，而不是只看最终态；
- 收敛轮数判定（默认最多 6 轮），未收敛即报"疑似抖动"；
- 断言从"原始路径"改为**语义不变式**（与 harness 版同一套）——第一版脚本断言
  "`assets/gif/pic.gif` 还在"，而重命名本是预期行为，于是把正常功能误报成"文件消失"。

### 4.5 关于「绕开 `fileManager.renameFile`，改用 `vault.rename` + 自己改写」的结论

**裁定：暂不改，保留 `fileManager.renameFile`。** 依据是这轮拿到的三条实测事实：

1. **"自己改写"这件事插件本来就在做，而且必须自己做。** 插件有 5 处在移动后自行改写引用
   （收集散落附件 / 收集全库 / 重命名笔记附件 / 笔记移动跟随 / 路径修复），原因是 Obsidian 的
   改名联动**对当前打开的那篇笔记常常不主动改写**。所以"改成自己负责"的增量成本并不大。
2. **但真正会丢数据的那条路已经堵住了，且不是靠 `fileManager`。** 原来的缺口是"共享误判为独占 →
   原地改名 → HTML 引用悬空"；它由 **§4.3 的索引口径合并**修好，而不是靠改名 API 的选择。
   本轮为此补了一枚守卫（safety-suite：单篇改名后**其它笔记**的 HTML 引用不得悬空），已验证通过。
3. **剩下的收益只是"少一个原生弹框"**，而那个弹框的代价可以一次性消掉：点一次「总是更新」即被
   记住，或在 Obsidian 设置里打开「自动更新内部链接」。为这点收益去自己复刻 Obsidian 的改名记账
   （标签页路径、索引缓存、事件语义、跨插件行为）不划算。

**什么情况下要重新考虑**：若有用户反馈"批量改名被这个弹框打断"是实际痛点，那它就从"外观问题"
升格为 UX 缺陷，届时再切 `vault.rename` + 全库改写——届时的安全网已经就位（§4.3 的守卫 +
safety-suite 的"改名后不得出现新断链"）。

## 6. 裁定记录（三阶段新增）

| # | 议题 | 裁定 | 理由 |
|---|---|---|---|
| E1 | 验收断言用"写死路径"还是"语义不变式" | 语义不变式（10 条） | 写死路径会被合法中间态大量误报，且证明不了真正要紧的性质（无损失、无新断链、越权零发生） |
| E2 | 引用写回时是否编码空格/圆括号 | 编码（`%20` / `%28%29`） | 裸空格在 CommonMark 中不是链接；Obsidian 自身也用 `%20` 形态。同时解析端两种形态都认 |
| E3 | 解析端是否对目标做 `%xx` 解码后再比对 | 是 | 否则含 `%20` 的引用既命不中"在用"集合、也命不中改名映射（两处都会出错） |
| E4 | 候选选择窗自动点哪个按钮 | `跳过`，绝不自动挑候选 | 多候选时自动挑等于替用户做决定，且可能把引用改到错误文件 |
| E5 | 是否修改 stub 的 `resolvedLinks`（比真实宽松） | 不改，由真实 Obsidian 兜底 | 改动牵动大量既有断言；风险收益不划算 |
| E6 | 自动化宿主无法稳定托管 GUI 进程 | 改为"人工一条命令启动 + 脚本自动驱动" | 崩溃与启动方式无关（0x80000003），非插件问题；不该为环境限制降低验收标准，也不该无限期卡住其他收尾 |
| E7 | 域名名单项粘贴 URL 的容错 | 解析阶段收口为纯主机名 | 带路径/端口写法分别导致"静默失效"与"过度拦截"，都属"看起来生效实际不符预期" |
| E8 | 真实宿主专属差异（命令 id 前缀 / 原生「更新链接？」弹窗 / 索引滞后） | 在**验收脚本层**吸收，不改插件行为 | 它们是宿主设计而非插件缺陷；插件的职责是在任何设置下都不丢数据，而这一点已由"层层不变式"守住 |
| E9 | "幂等"的口径 | 改为「**有限轮内收敛**」 | 命令顺序里"收集"在"重命名"之前，本轮命名出的文件要等下一轮收集才落位；要求"第一遍后零变化"是把固有交互当缺陷 |
| E10 | 空目录判空的依据 | 回查**真实文件系统**（`adapter.list`），读不到按非空处理 | 库索引不含点文件，`.gitkeep` 这类用户明确要留的占位文件会被连带目录删掉 |
| E11 | 附件引用的两套口径（Obsidian 解析结果 / 插件文本扫描） | **合并**，不再"二选一" | 只取其一会在"部分重合"时丢掉一方（HTML 标签引用），进而把共享误判为独占、引用悬空 |
| E12 | 验收断言用"原始路径"还是"语义不变式" | 语义不变式（含真实宿主脚本） | 重命名是预期行为；按原始路径断言会把正常功能误报为"文件消失" |
