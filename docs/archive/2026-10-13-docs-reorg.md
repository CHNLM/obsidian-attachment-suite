读者分不清哪句还算数，作者则不断往里加"范围声明"补丁（`coverage-audit` §2–§7、
`security-threat-model` 的行号声明、`review-phase1/2` 的"历史归档"标签都是这类补丁）。
**重组的核心动作就是按这个判据把两类内容彻底分开。**

## 附录 A · 方案 A（手写 + 机器对账）与「文档生成物化」的对比

> 决策点 6 的展开。**结论先说**：在本仓库，二者**不是互斥的替代关系，而是"覆盖不同内容"的互补关系**——
> 生成物只能覆盖 **5–10%** 的内容（机械事实），而 docs 的主体是**判断、理由与历史**（不可生成）。
> 全仓转向生成物**不成立**；局部生成**值得**，但它省的是"手填值"，不是"写文档"。

### A.1 两条路线到底是什么

| | **方案 A：手写 + 机器对账** | **生成物：机器写 + 人只读** |
|---|---|---|
| 核心思路 | 人写文档（含判断与理由），**机器校验**它与代码是否一致；不一致就**红** | 事实从代码**推导**并**写回**文档；人不再编辑那部分 |
| 信息来源 | 人（判断）**+** 代码（事实），两者**互为约束** | 只有代码 |
| 冲突时的表现 | 测试红、指出**哪一行**漂移 → 人必须二选一：改代码或改文档 | 不存在冲突（文档**就是**代码的投影） |
| 典型形态 | 本仓现在就是这样 | `--help` 自动生成、OpenAPI → 参考页、从 `DEFAULT_SETTINGS` 渲染配置表 |

### A.2 一个本仓特有的事实：**生成器其实已经写好了**

`docs-consistency.test.ts` 里那份"默认值对账"的映射表，长这样（第 477–529 行附近）：

```ts
const MAP: Array<[string, () => string]> = [
  ['统一命名',   () => onOff(S.naming.enabled)],
  ['通知级别',   () => notifyLevel[S.notificationLevel]],
  ['删除方式',   () => deleteMode[S.cleanup.deleteMode]],
  // …共 38 行
];
```

**这些 `() => …` 就是渲染函数**——也就是"生成器"。本仓只是把它用来 `expect(same(cell, want))`（比对），
而不是 `writeFile(...)`（写出）。**所以"转向生成物"在本仓的技术门槛极低**：
把 `expect` 换成"写回文档的那一格"，工作量以**小时**计。
**真正的问题不是"能不能生成"，而是"生成得出来的东西值不值得"**（见 A.3）。

### A.3 能生成多少？——逐篇盘一遍

| 文档 | 行 | 可机械推导的部分 | 占比 |
|---|---|---|---|
| `default-settings.md` | 201 | 「默认」列的值（≈30 个单元格） | ~15% |
| `command-inventory.md` | 173 | 命令 id / 名称（14 行） | ~10% |
| `coverage-matrix.md`（原 coverage-audit） | ~200 | 用例计数、"有/无覆盖"的**原始证据**（可扫测试名） | ~40%（且判断仍需人写） |
| `invariants.md` | 233 | **0** | 0% |
| `security-threat-model.md` | ~300 | **0** | 0% |
| `records/`（逐轮记录） | ~1200 | **0** | 0% |
| `archive/`（历史过程） | ~2200 | **0** | 0% |
| **合计** | ~4500 | | **≈5–10%** |

**为什么这么低**：本仓文档的价值**不在"值是多少"，而在"为什么是这个值"**。
`default-settings.md` 的三十多行里，每行都跟一句"不改会怎样"；`invariants.md` 全是教训与判据；
`archive/` 记的是"当时踩了什么坑"。**这些没有一个能从代码推导出来。**

### A.4 优势 / 局限

| | 方案 A | 生成物 |
|---|---|---|
| **优势** | ① 能承载**判断、理由、教训、历史**（本仓 90% 的内容）② 能被**评审**——PR 里 diff 是文本，评审者读的就是最终产物 ③ 已有 8 类守卫把关，漂移**必被机器发现** ④ 不引入构建期依赖 | ① **物理上不可能漂移**（文档即投影）② 事实变更**零手工**（改代码即生效）③ 适合**多下游消费**（多语言 / 多版本矩阵 / 站点） |
| **局限** | ① 事实变更要**人记得改文档**（靠守卫兜底，但守卫本身要维护）② 守卫与被校对象**互为耦合**（改文档结构要同步改守卫） | ① 只能覆盖可推导部分（本仓 ~5–10%）② 判断与历史**无处安放** → 要么仍手写（那就回到 A，只是不入库，**更糟**）③ **失效模式是静默的**：生成器漏掉一类事实时，没有任何断言会红（**等价于把守卫的成本转嫁给了生成器**）④ 评审对象从"文档"变成"生成器"，可读性下降 |

### A.5 关键差异（一句话）

> **A 是「人写、机器校」——能承载判断与历史，代价是可能漂移（但可被发现）。**
> **生成物是「机器写、人不改」——不可能漂移，代价是只能承载可推导的事实，且失效是静默的。**

两者最容易被忽略的差异在**失效模式**：A 漂移后**有信号**（测试红）；生成物的对应风险是"生成器不全"，
而**那件事没有守卫**——除非你再为生成器写一份守卫，于是成本又回来了。

### A.6 什么条件下选哪个

**优先选「局部生成物」的条件（满足任一即值得对那一处生成）：**

1. **事实纯机械、零判断**（例：`command-inventory` 的 id 列、`default-settings` 的值列）。
2. **变更频率高到"人写必然漂移"**（例：设置项还会持续增加）。
3. **有多个下游消费者**（例：将来上社区市场，要出中/英两版设置说明）。
4. **出现第二个维护者**，且他会忘记同步文档（新增"人"这一环＝新增一个漂移源）。

**优先保持「方案 A（手写 + 对账）」的条件：**

1. 内容里**判断与理由占多数**（本仓：90%+）。
2. 需要**追溯历史**（`records/`、`archive/` —— 它们本质是事实，但**是过去的**事实，无从推导）。
3. 仓库有**强自律的单一维护者**且已有守卫把关键事实钉住（本仓现状）。
4. 需要**把文档本身当作评审对象**（安全评审、威胁模型、决策记录）。

### A.7 对本仓库的结论与建议

1. **全仓转向生成物：不推荐。** 只能覆盖 5–10%，却要放弃"判断与历史"的承载能力；
   且 `records/`、`archive/` 这类**过去的事实**在任何方案下都生成不出来——它们只能手写保存。
2. **局部生成：推荐，但优先级低于本次重组。** 最先值得做的是
   `command-inventory.md` 的**清单列**（id/名称）与 `default-settings.md` 的**值列**——
   做法是把这两处包围在标记区块里（如 `<!-- gen:start -->…<!-- gen:end -->`），
   新增一个 `npm run docs:gen` 只重写区块内内容，**区块外的手写理由一字不动**；
   守卫改为"校验区块已同步"。**注意**：这会把守卫的职责从"校验"变成"校验+生成"，**必须保留校验**
   （否则生成器一旦漏项就静默失效）。
3. **不要为了"能 gitignore 手写文档"而转向生成物。** 那条路的净效果是：
   判断与历史**移出仓库** → 与"历史已压缩为单条提交、reflog 已清"叠加 → **彻底失去可追溯性**，
   而换来的只是"少提交 441 KB"。**收益与代价严重不成比例。**
4. **升级触发条件（出现任一再回头重新评估）**：① 上社区市场需要多语言文档；
   ② 设置项或命令数继续显著增长；③ 出现第二位维护者。

### B.2 6-B 的本质：它是**工效**优化，不是**正确性**优化

- **收益侧**：省下的是"约 **50 处**机械事实的手填"（`default-settings` ≈38 个值单元格 +
  `command-inventory` ≈14 行 id/名称）。**仅此而已。**
- **成本侧**（四项，都要付）：
  1. **写入路径**：现在只有"读+比"，要新增"写"。写路径**错了没有断言能发现**——
     因为"生成出来的值"按定义就是"正确的"。要发现它，只能**再比对一次**。
  2. **比对仍然必需**：否则"忘了跑 `npm run docs:gen`"就静默漂移 →
     于是你得到的是"**生成器 + 与现在完全相同的对账守卫**"，**代码严格变多、保证没有变强**。
  3. **格式脆弱**：不得为生成 Markdown 引入 remark/mdast 之类的依赖（本仓运行时/构建期都很克制），
     只能用正则/拼接 → 一旦有人手工调整表格格式，生成器可能**写坏**。
  4. **评审噪声**：PR 的 diff 里出现"生成区块被整体重写"，会淹没真正的改动。
- **结论**：**只有当"手填成本 > 生成器 + 新守卫的维护成本"时才划算**。
  本仓现在是 **~50 处、每次发版变几次**——**没有过这条线**。

### B.3 6-B 与 3-B 的**实质冲突**（最重要的一条）

3-B 要**新写** `specs/coverage-matrix.md`，而 6-B 的胃口是"凡是机械事实就生成"。
矩阵里最机械的东西**恰好是用例计数**（`coverage-audit` §3 那张"82 条中 43 条被机器校验"的表）。

- **冲突**：计数一旦由生成器产出，就出现**第二个"用例数"来源**，而本仓有一条明确规矩
  （已由守卫强制）：**规模类数字只有一个权威来源 = `tests/README.md` 第 8 行**。
  两个来源**必然**漂移，且守卫**管不住**（它只知道"其它文档不得复制数字"）。
- **处置**：**6-B 的适用范围必须显式排除覆盖率/计数类内容。**
  `coverage-matrix.md` 只写"某功能**有没有**覆盖"（定性）+ 指向 `tests/README.md`（定量），
  **一个数字都不要自己出**。

### B.4 6-B 与 1-A / 5-A 的耦合（形态必须先定死）

- **形态**：局部生成有两条路——
  - **(i) 写回源文件并提交**（区块包裹：`<!-- gen:start -->…<!-- gen:end -->`）。
    → **唯一可行**：文件仍在仓库里，CI 的守卫读得到；守卫职责从"校验手写"变为
    **"校验生成区块已同步"**（几乎不变）。
  - **(ii) 生成到别处（`dist/` 或 `docs/generated/`）、源文件 gitignore 生成物、或用 include 引用**。
    → **不可行**：Markdown 没有 include（要么引依赖）；生成物不入库则 **CI 里不存在 → 守卫读不到 → 红**。
- **提交切分**：5-A 现在切成"① 搬迁合并 / ② 引用与守卫同步"。**6-B 必须是独立的第 ③ 个提交**
  （生成器脚本 + 区块改造 + 守卫改造 + 开发流程文档）。理由：②已经在改守卫，
  两拨守卫改动混在一起，出问题时**无法判断是哪一拨**。
- **1-A 的联动**：区块化之后，`specs/command-inventory.md` 里**同时存在手写与生成两种内容** →
  它的**文件头必须写明哪一段是生成的**，否则维护者会手改生成区块、然后被下次生成覆盖。

### B.5 风险清单

| 风险 | 触发条件 | 后果 | 缓解 |
|---|---|---|---|
| 生成物不入库 → CI 守卫红 | 选 B.4(ii) | 发版被堵 | **只允许 B.4(i)** |
| 第二个"用例数"来源 | 6-B 覆盖到矩阵计数 | 数字漂移且守卫管不住 | **显式排除计数类内容**（B.3） |
| 忘了跑生成 → 提交了过期区块 | 生成器 + 无守卫 | 静默漂移（**回到今天要解决的问题**） | **保留并改造对账守卫**为"校验区块已同步" |
| 生成器写坏表格 | 依赖正则/拼接 + 有人手调格式 | 文档结构损坏，且无断言 | 生成区块用**最简格式**（纯文本行或两列），并在守卫里加"区块头尾标记唯一且成对" |
| 守卫改动互相掩盖 | 6-B 与 5-A② 同提交 | 无法定位回退点 | **拆成第 ③ 个提交** |
| 收益为负 | 机械事实数量少 | 白付维护成本 | 见 B.6 的触发条件 |

### B.6 调整建议（三档）

| 档 | 内容 | 适用 |
|---|---|---|
| **建议 1（推荐，成本最低）** | **6 改回 A**：本次不做生成，只把 6-B 作为**"待触发项"登记**（触发条件用附录 A §A.6 的四条）。组合变为 **1-A/2-A/3-B/4-A/5-A/6-A** | 当前状态——**正确性已由守卫保证，6-B 只省手填**，而 6-B 还要新增写入路径 + 守卫改造 + 第③提交 |
| **建议 2（若坚持局部生成）** | **收窄到只做 `command-inventory.md` 的命令表**（14 行 `id | 名称 | 功能`），**不碰 `default-settings.md`**（它的"默认值"与"理由"同表，生成收益最低、耦合最高）；形态固定为 B.4(i)；独立第③提交；守卫改为"校验区块已同步" | 认为"新增命令忘登记"是最高频的漂移点，且愿意付一次改造成本 |
| **建议 3（不推荐）** | 对 `default-settings.md` 的值列也生成 | 收益（38 格）与耦合（与理由列同表、需同步 `MAP` 与完备性规则）不匹配 |

### B.7 调整后的组合

**推荐：`1-A / 2-A / 3-B（排除计数类内容） / 4-A / 5-A / 6-A（6-B 登记待触发）`**

理由归纳为一句话：
> **本仓的"机械事实"已经零漂移，6-B 换不来正确性，只能换来"少填约 50 处"；
> 而它要付出"写入路径 + 生成器守卫 + 第 3 个提交 + 评审噪声"。在这个规模下不划算。**

若采纳**建议 2**，组合为 `1-A / 2-A / 3-B（排除计数） / 4-A / 5-A（3 个提交） / 6-B（仅命令表）`——
**必须同时满足**：B.4(i) 的形态、B.3 的排除、B.4 的独立提交、B.5 的守卫保留。
