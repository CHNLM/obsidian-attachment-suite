### 1.1 L1.3 的落地形态与方案不同（已记录偏差）

方案设想给每个 `AcceptanceCase` 加一个 `assert` 函数；实际改为**独立的 `ACCEPTANCE_ASSERTS` 表**：

- 好处一：一眼可见"哪些用例还没有机器校验"（表的键数就是已校验条数）；
- 好处二：可以加"表里的 id 必须都真实存在于用例清单"的守卫。**这条守卫本身就是必要的**——
  拼错 id 的断言会静默永不执行，而"看起来在跑、实际什么都没校验"正是本次复查反复遇到的失效模式。

## 2. 实施期新发现的 P0：canvas 引用的附件被整条吃掉（提交 `7efe898`）

### 2.1 怎么发现的

L1.5 把 O06（"仅被 canvas 引用的附件不得被判孤儿"）从**同义反复**改成**字节指纹判定**后，
验收套件立刻报出两条"内容在库中消失"——其中一条正是 `orphans/only-canvas.png`。

> 旧的断言是 `files.some((f) => f.includes('canvas') || f.includes('frontmatter'))`，
> 而库里必然存在 `canvas/画布用例.canvas` 与 `notes/04-frontmatter.md`，**恒真**。
> 这个缺陷因此藏了很久。

### 2.2 完整因果链（探针实测，逐步复现）

| 步骤 | 文件 | canvas 的 `file` 字段 |
|---|---|---|
| 初始 | `orphans/only-canvas.png` | `orphans/only-canvas.png` |
| `收集当前笔记附件` | `canvas/assets/only-canvas.png` | **仍是旧路径（未被改写）** |
| `重命名全库附件` | `canvas/assets/画布用例_image_001.png` | **仍是旧路径** |
| `清理未用附件` | **`.trash/画布用例_image_001.png`（被删）** | 仍指向已不存在的位置 |

**根因**：插件的**索引层**把 canvas 的 `file` 节点算作"在用"
（`core/attachment-index.ts` 的 `canvasFileRefs`），但**改写层完全不认识 canvas**——
`rewrite()` 只认 markdown/wiki/HTML，`rewriteRefsInNote` 只额外处理 frontmatter。
于是"搬走 + 改名"之后引用悬空，而清理层依据同一套（已经悬空的）引用关系判定"没人引用我"，把文件删掉。
**这是本仓库第 5 次同源的"两层口径不一致"。**

### 2.3 修复

1. `rewriteCanvasFileFields` 从 `features/broken-link-core` **归位到 `core/link-resolver`**
   （需要它的既有 feature 的断链修复，也有 infra 的通用兜底改写，而 infra 不允许 import features）。
2. `obsidian-domain.rewriteRefsInNote` 改为**按文件类型选改写器**：md 走 `rewrite + rewriteFrontmatter`，
   canvas 走 `rewriteCanvasFileFields`。
3. `broken-link.ts` 的逐篇改写改走 `rewriteRefsInNote`，**删掉自建的那套分支**（同一件事两份实现）。
4. 顺手修掉 `rewriteCanvasFileFields` 自身的一个缺陷：旧实现是 `text.split(from).join(to)`，
   在映射同时含"完整路径"与"纯 basename"两项时（`refMapForMoves` 正是这么造的）会**二次替换**，
   把 `canvas/assets/a.png` 改成 `canvas/assets/canvas/assets/a.png`。
   改为只整值匹配 `"file"` 字段，天然幂等，也不误伤其它字段里相同的字符串。

### 2.4 验证

- 单元测试 +4 条（二次替换回归 / 幂等 / 不误伤其它字段 / 保留缩进）。
- E2E +1 条：`safety-suite` E 组「收集 + 命名 + 清理」链路。
- **变体测试**：把 canvas 改写回退后，验收套件的全局不变式与 N17 立刻转红
  （`canvas 出现新断链：可解析引用 1 → 0`），确认守卫可证伪。

同时补上了让这个缺陷"隐身"的**不变式缺口**：`localRefs` 现在也解析 canvas 的 `file` 字段，
`beforeTexts` 也纳入 `.canvas` 文件——否则"canvas 引用变成断链"这条永远不在扫描范围内。

## 5. 仍然遗留（诚实登记）

| # | 事项 | 为什么现在不做 |
|---|---|---|
| R1 | `acceptance.test.ts` 的 `ACCEPTANCE_CASES[].expect` 仍有 **52/77** 条没有机器校验 | 本轮已从 0 → 25。剩余多数需要"逐命令观察"或"与执行前对比"，得为每条设计上下文；建议按利用率逐步补，并保持"未校验条数"可见 |
| R2 | 「无新断链」不变式对 **HTML 属性里的路径式引用**仍按路径解析（与 md 同档），未区分 `<img src>` 的 Obsidian 解析语义 | Obsidian 对 HTML 属性不做链接解析，故其解析语义本质上是"浏览器相对路径"；当前按路径判定是**偏严**的一侧（宁可报错不放过），风险方向安全 |
| R3 | `useMarkdownLinks` 只覆盖了"本地化改写"两个分支，未覆盖「命名/收集」等其它产出链接的命令 | 那几处的链接形态由 `refMapForMoves` + `rewrite` 决定，与 `useMarkdownLinks` 无关（插件统一按库内路径写），故没有额外的分支可测 |
| R4 | 真实 Obsidian（CDP）那一遍验收未在本轮重跑 | 需要**人工**双击 `Attachment Suite/scripts/launch-obsidian-debug.cmd` 启动宿主后由脚本接管（自动化启动会崩溃）。canvas 修复在真实宿主上的表现建议顺带验一次 |
| R5 | `scale.test.ts` 只有下界断言（`toBeGreaterThanOrEqual`） | 规模基线的作用是"发现性能退化"，不是正确性；改为精确区间会在不同机器上抖动 |
