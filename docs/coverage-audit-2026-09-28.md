# 覆盖审计：验收用例 vs 插件全部功能

> 日期：2026-09-28 ｜ 针对对象：验收库（82 条验收用例，本地生成）+ 真实宿主脚本 + 其余测试层
> 结论先行：**不全面。** 82 条用例覆盖的是"**输入形态的多样性**"，不是"**功能分支矩阵**"；
> 而真实宿主那一遍跑的是 **13 条命令 × 一套默认配置**，自动化、笔记移动跟随、设置页、
> 两种删除模式、以及绝大多数设置的非默认分支都不在其中。

---

## 1. 三层覆盖结构（先说清"哪一层验了什么"）

| 层 | 载体 | 验的是 | 盲区性质 |
|---|---|---|---|
| 单元 | `tests/unit/**`（含 pure core） | 纯逻辑（命名、解析、相似度、路径规则…） | 不接触 Obsidian，无法发现"与宿主交互"的问题 |
| harness E2E | `tests/e2e/**`（替身 `infrastructure.ts`） | 命令行为、设置页、通知契约、落盘位置 | **替身可能比真实宿主更强**（已 4 次踩中） |
| 真实宿主 | `scripts/obsidian-cdp-acceptance.mjs` | 13 命令 × 收敛轮次 + 引用形态 + 幂等 | 只有**一套配置**、**固定命令顺序**、无界面交互 |

**关键认知**：真实宿主那一层是"最终防线"，但它的**断言面比 harness 窄**——
它断言"库没被改坏"，不断言"功能按预期生效"（例如它不读报告弹窗内容、不读通知文案）。

## 3. 用例侧覆盖：82 条的机器校验分布

82 条用例中，**只有 30 条**在 `ACCEPTANCE_ASSERTS` 里被机器校验；
其余 **52 条**仅受 11 条全局不变式保护（"没被改坏"），**其 `expect` 里写的"应该变成什么样"没有被执行过**。

| 类别 | 总数 | 机器校验 | 仅靠全局不变式 |
|---|---|---|---|
| 笔记形态 | 20 | 5 | 15 |
| 附件形态 | 16 | 4 | 12 |
| 外链 | 18 | 9 | 9 |
| 孤儿 | 7 | 7 | 0 |
| 空目录 | 5 | 5 | 0 |
| 目录布局 | 6 | 0 | 6 |
| 路径 | 2 | 0 | 2 |
| 幂等 | 6 | 0 | 6 |
| 自动化 | 2 | 0 | 2 |
| **合计** | **82** | **30** | **52** |

11 条全局不变式（`acceptance.test.ts` 与 CDP 脚本各一份，口径已由 `acceptance-tooling` 守卫同步）：
① 该弹确认的必须真弹；② 非受管文件原封不动；③ 排除目录整块不动；④ **无新断链**（核心）；
⑤ 受管附件数不得低于被引用数；⑥ 外链已本地化（白名单内）；⑦ 保形改写（HTML/普通链接）；
⑧ 命名生效；⑨ 真孤儿被清理且 zip 不被当附件清理；⑩ 空目录矩阵；⑪ 有限轮内收敛 + 无 `(N)` 抖动。

> 注意：**"只受不变式保护"不是"没被验证"**，而是"只验证了没变坏，没验证变成想要的形态"。
> 目录布局 6 条、幂等 6 条、路径 2 条、自动化 2 条**整类都没有机器校验**。

## 4. 设置项覆盖：45 项 × 1 套配置

`DEFAULT_SETTINGS` 共 **45 个叶子键**（其中 `version` 不是用户设置，实际可配置项 **44**）。
真实宿主只用**一套** `ACCEPTANCE_SETTINGS`，与默认值不同的是这 12 处
（多为网络与正文扫描相关，**功能开关类几乎全是默认值**）：

`attachmentFolderMode='custom'`、`exporter.enabled=true`、`automation.enabled=**false**`、
`paths.exclude=[…]`、`notificationLevel='verbose'`、`scanHtmlAndLinks=true`、
`blockPrivateHosts=false`、`useMd5ForNew=false`、`maxConcurrent=2`、`tryCount=1`、
`timeoutMs=5000`、`denyHosts=['blacklisted.invalid']`。

于是下面这些**只在"默认一侧"被真实执行过**，其非默认分支从未在真实宿主上跑：

| 设置 | 非默认分支从未在真实宿主验证 |
|---|---|
| `naming.folderByCategory` | `true`（按类别子目录） |
| `naming.addTime` / `addPathHash` / `showSubType` | `true` |
| `naming.enabled` / `localize.enabled` / `consistency.enabled` / `cleanup.enabled` | `false`（关闭后命令应早退） |
| `localize.blockPrivateHosts` | `true`（验收里是 `false`，故 E06 走的是"连不上→保留原文"而非"拦截"） |
| `localize.hostAllowlistOnly` | `true` |
| `localize.minSizeKb` / `maxDownloadMb` | `>0`（体积门槛） |
| `localize.perHostIntervalMs` | `>0`（限速） |
| `localize.tryCount` / `timeoutMs` | 重试与超时边界（验收是 1 次 / 5000ms） |
| `localize.useMd5ForNew` | `true`（验收是 `false`） |
| `consistency.platforms` | `mac` / `linux` 规则 |
| `consistency.followNoteMove` | `true` |
| `consistency.fuzzySuggest` | `false`；以及候选"选定并修复"的动作 |
| `cleanup.deleteMode` | `system-trash` / `permanent`（且**全仓库零用例**） |
| `cleanup.requireConfirm` | `false`（无确认直接删） |

| `debugLogging` | `true`（已人工验证一次，见报告第 8 节） |

## 5. 缺口清单（按风险排序）

**P0 — 不可逆且零覆盖**
1. `cleanup.deleteMode = 'system-trash'` / `'permanent'`：**两种删除方式没有任何行为用例**。
   `.trash` 走 `vault.trash`，另两种走 `trash(true)` / `delete`，是**完全不同的代码分支**，
   且失败后果不可逆。"永久删除"尤其危险：一旦路径判断出错，用户没有回收站可救。

**P1 — 真实宿主未验、且属于"用户最常用的默认路径"**
2. `attachmentFolderMode='obsidian'`（**默认值**）的落盘位置：真实宿主从未跑过。
   harness 的 `vault-config` 覆盖了 6 格，但那一层用的是替身的 `getConfig`，
   而这一处历史上正是"替身替插件兜底"的重灾区。
3. 自动化后台处理：真实宿主全程 `enabled=false`。它涉及定时器、`metadataCache` 事件节流、
   队列与并发——**正好是最容易出"真实宿主才复现"问题的地方**（本次的目录缺失缺陷就属这类）。

**P2 — 分支/断言面缺口**
4. 断链候选的**"选定并修复"**：真实宿主只走"跳过"。
5. 删除前确认弹窗的两种路径（确认 / 关闭）中，"关闭确认"分支在真实宿主上未验。
6. 一致性报告与通知**内容**在真实宿主上未验（脚本不读弹窗与提示文案）。
7. `reveal-ref`（报告里点击定位到断链所在笔记）：**全仓库零用例**。
8. 52/82 条用例无机器校验（尤其目录布局 6、幂等 6、自动化 2、路径 2 整类为零）。

## 6. 建议的补齐顺序

| 顺序 | 动作 | 防住哪类缺陷 |
|---|---|---|
| 1 | 给 `cleanup.deleteMode` 另两种模式各加一条 harness 用例（断言"文件确实不在原处"，`permanent` 额外断言不产生 `.trash` 项） | 不可逆分支从未执行 |
| 2 | 真实宿主验收加一个**"默认配置轮"**：`attachmentFolderMode='obsidian'` + 其余尽量用默认，与现有"custom 轮"各跑一遍 | 默认路径从未在真实宿主验证 |
| 3 | 真实宿主把 `automation.enabled=true` 纳入（用短间隔 + 等待其自动处理若干笔记，断言"自动处理确实发生过"） | 定时器/事件/队列类问题只在真实宿主暴露 |

| 6 | 为 `reveal-ref` 加一条用例（替身层面可断言"调用了打开笔记的接口"） | 唯一全零覆盖的功能 |

## 7. 一句话方法论

**"用例数"不等于"覆盖度"。** 82 条用例回答的是"各种输入形态下库会不会被改坏"，
而不是"每个功能分支是否按预期工作"。两者都要，但**判断缺口必须按"能力 × 分支"去看，
而不是按用例数去看**——本次审计里最危险的三处缺口（两种删除模式、默认落盘模式、自动化）
在 82 条用例里各有"看着像"的邻近用例，实际上从未执行。

### 补齐过程本身又换来一个真实缺陷（数据损失）

新断言 `L06`/`P01` 第一次运行就报红，在真实验收库核对后确认：`path-cases/normal name (1)-ok.png`
被「清理未用附件」**移入 `.trash`**，笔记留下断链。根因是 markdown 目标捕获写成 `([^)]*)`
——在 `(1)` 的 `)` 处截断，截断后的目标既不进"在用"集合、也无法被改写。

- 修复：`MD_DEST = ((?:[^()]|\([^()]*\))*)`（允许一层括号嵌套），harness 与 CDP 脚本同步，
  `acceptance-tooling` 守卫加第 5 项标记防退化。见提交 `8415579`。
- 真实宿主复核：附件正常改名为 `path-cases/assets/合法名字保持_image_001.png`（**没进回收站**），
  引用同步改写。
- 这是"把 `expect` 真正执行起来"的直接收益：**同一条用例在 82 条里躺了很久，
  只受全局不变式保护，而那条不变式恰好也被同一个解析缺陷蒙住了**。

## 9. X02 的风险定级（2026-09-29）

被问到"X02 未覆盖对功能验证影响大吗"。定级结论：**覆盖形式上它是最严重的一处，功能影响上它是小的**。

### 9.1 它不是"没断言"，而是"整条分支不可达"

```ts
// src/main.ts
const STARTUP_SUPPRESS_MS = isTestEnv ? 0 : 1500;   // ← 测试环境恒为 0
// main.ts:172
if (STARTUP_SUPPRESS_MS > 0 && Date.now() - this.automationReadyAt < STARTUP_SUPPRESS_MS) return;
```

`isTestEnv` 由 `globalThis.__OBSIDIAN_TEST` 判定，而**每个 E2E 用例都注入它**（8 个测试文件都读它）
→ 常量恒为 0 → `STARTUP_SUPPRESS_MS > 0` 恒假 → **第 172 行在任何测试里一次都不执行**。

这与"52 条用例没有机器校验"不是一回事：那 52 条至少被观察过（受全局不变式约束）；
这一处是**代码路径本身不进测试**——删掉它、改坏它、把窗口改成 0，**全套 427 个用例依旧全绿**。

### 9.2 失效的后果（为什么它值得单独说）

自动化路径不弹确认框：

```ts
// features/automation.ts:50
const r = await runRenameNote(app, index, getSettings, mover, false, notePath, undefined, false);
//                                                     ↑ confirm=false      ↑ notify=false
```

失效链条：打开库 → Obsidian 对全库触发 `metadataCache.changed` → 全部 md/canvas 被标脏
→ 1 秒后轮询逐篇 `runAutoProcess` → **整个库的附件被改名、搬进各笔记的归属目录，全程无确认**，
用户只会在事后看到一串 Notice。

这是本插件**唯一一条"未经用户同意就批量改写整库"的路径**。而本仓库已有 7 次"引用改写口径不一致"
的记录（每次都造成数据损失）——一旦某个残留缺陷落在批量路径上，影响面会从"一篇笔记"放大到"整个库"。

### 9.3 但概率低（"影响小"的那部分）

分支只有一行时间比较，参数是常量。能弄坏它的方式很少：删掉该行、把 `STARTUP_SUPPRESS_MS` 改成 0、
把 `automationReadyAt` 的赋值挪到窗口判断之后——都属于"人工改动才会发生"，不会被日常重构顺带碰坏。

### 9.4 真正没被回答的问题（比覆盖数字更值钱）

**`1500ms` 这个值从来没被验证过。** 它是启发式：假定 Obsidian 在插件 ready 后 1.5 秒内完成
对全库的 `metadataCache.changed` 批量触发。对大库 / 慢盘 / 插件多的环境，初始索引完全可能超过
1.5 秒——那么**迟到的 changed 事件仍会把全库标脏，抑制窗口形同虚设**，9.2 的后果照旧发生。

这不是覆盖缺口，而是**可能存在的真缺陷**，且只能在真实宿主上回答——恰好是 X02 专用观测能一次
解决的事：用一篇 canary 笔记做标记，启动后**立刻**（跑任何命令之前）断言它没被动过；再等到窗口
过期后复查一次（负向对照，证明"通过"不是因为整个自动化没生效，而是抑制真的起了作用）。

### 9.5 建议

| 判断 | 结论 |
|---|---|
| 对"插件功能是否被验证" | 影响**小** —— 受保护的是"少做一件事"，逻辑仅一行 |
| 对"是否还有假绿" | **它是最典型、也是最后一处** —— 唯一"测试根本碰不到"的分支 |
| 对"是否漏掉真缺陷" | **中等** —— 1500ms 的充分性从未被任何方式验证 |
| 成本 | 约 40 行（canary 笔记 + `--startup-check` 阶段），一次真实宿主运行约 1 分钟 |

**推荐做**，但理由不是补覆盖率数字，而是 9.4——它是目前唯一还可能藏着真缺陷的时序点。

## 10. X02 的处置：实测确认 → 两道防线 → 真实宿主复现验证（2026-09-29）

### 10.1 结论修正：9.4 的猜测被证实，缺陷是真的

第 9 节我把它定级为"功能影响小"。**实测支持"必须重视"这一判断**：启动期批量事件真实存在，
规模就是整个库；一旦漏进自动处理，就是"用户只是打开了 Obsidian，附件被改名搬走"。

### 10.2 实测：启动期到底有多少事件（`getAutomationDiagnostics()` 取证）

带 automation 打开验收库（48 篇笔记）：

| 计数 | 值 | 含义 |
|---|---|---|
| `suppressedNotSettled` | **49** | 就绪**前**被挡下的 changed（≈ 每篇笔记一个） |
| `suppressedQuiet` | **46** | 就绪**之后**的余震窗口内被挡下的 |
| `settleSource` | `metadataCache.resolved` | 就绪信号来自宿主事件，**不是**兜底超时 |
| `readyAt → settledAt` | **70ms** | 插件随宿主启动加载，索引在它之后才完成 |
| 笔记改写 | **0** | 打开库没有改写任何一篇笔记 |

启动期共 **95 次 changed**，其中 **46 次发生在 `resolved` 之后**。
→ 这条数据直接否掉了"只靠 `resolved` 一个信号"的简化方案：**余震窗口是必需的**，
没有它会有 46 篇笔记被标脏（进而触发批量护栏，用户每次开库都看到一条"已跳过 46 篇"的告警）。

### 10.3 两道防线（`src/features/automation-core.ts`）

| # | 防线 | 判据 | 为什么这样定 |
|---|---|---|---|
| ① | **条件式就绪门** | `metadataCache.resolved` 之后再过 `postSettleQuietMs`（1.5s） | 时长随库自适应，替代"固定 1500ms"这个在大库上会失效的启发式 |
| ② | **批量护栏（fail closed）** | 单次轮询待处理笔记数 > `maxPerSweep`（5） | 一次间隔内真人不可能编辑 5 篇以上；库索引刷新/同步工具/批量脚本都不是"用户正在编辑"的证据 |

配套三点：
- **兜底放行**：宿主不发就绪事件时，`settleDeadlineMs`（8s）后按已就绪处理并记 warn——
  否则自动处理永久失效，那是另一类缺陷（"承诺了却不生效"）。它只影响可用性，不影响安全性。
- **可取证计数 + `getAutomationDiagnostics()`**：这类防线保护的是"没发生的事"，
  "什么都没发生"无法自证。有了计数，真实宿主才答得出"这道门到底挡下了什么"。
- **拒绝服务必须可见**：护栏触发时用 error 级 Notice（`shouldNotify` 里错误在任何档位都提示），
  并说明"为什么跳过"与"那该怎么办（手动执行命令）"。

**测试可见性同步修复**：旧实现是 `STARTUP_SUPPRESS_MS = isTestEnv ? 0 : 1500`，
测试环境下该分支**一次都不执行**。现在删掉了这个测试特判，改由替身发出
`metadataCache.resolved`、并允许用例覆盖 `automationGuard` —— 这条路径在 harness 里可达可测。

### 10.4 真实宿主上的变体实验（决定性）

用 `--startup-check` 在真实 Obsidian 上做对照（每次都是重新 seed 的干净库、automation 在启动时即开启、
全程不做任何操作）：

| 变体 | 笔记改写 | 哨兵附件 | 批量护栏拒绝 | 判读 |
|---|---|---|---|---|
| **完整实现** | **0 篇** | 完好 | 0 次 | 打开库没有改写任何东西 |
| 只关就绪门（护栏保留） | 0 篇 | 完好 | **1 次** | 批量事件**确实会漏进轮询**；护栏挡住了 → 护栏是load-bearing的 |
| 门 + 护栏都关 | **31 篇** | **已消失** | 0 次 | **缺陷真实复现**：仅"打开库"就改写 31 篇、附件被改名搬走 |

第三行就是那个"看似轻"的后果。这也是 X02 这条断言**非空洞**的证明：
它从 0 变到 31 篇 + 哨兵消失，并精确报出被改写的路径。

补充：第二行还说明**两道防线各有各的职责**——护栏能保住库不被改写，
但用户会每次开库都收到一条"检测到 46 篇同时待处理，已跳过"的告警；就绪门才是让这件事压根不发生的那一层。

### 10.5 交付

- `src/features/automation-core.ts`（新，纯决策逻辑）+ `tests/unit/features/automation-core.test.ts`（10 条）
- `src/main.ts`：删掉测试特判；接上就绪门、护栏、诊断计数与 `getAutomationDiagnostics()`
- `tests/e2e/real-suite.test.ts` 第 20 组（5 条）：未就绪不处理 / 对照（就绪后正常处理）/

## 12. 文件右键菜单入口（2026-09-29）

命令面板之外，为**笔记级命令**加了第二条入口：在文件浏览器里右键一篇笔记，
菜单底部多出四项（收集 / 重命名 / 本地化 / 导出当前笔记附件）。

**为什么是文件菜单而不是 ribbon**：这些命令的作用对象是"某一篇笔记"，
而右键正是用户表达"我要对**这个文件**做点什么"的时刻——上下文自带目标，无须先打开它，
也不占常驻界面。ribbon 留给全局体检类（如「检查库一致性」）更合适，本次未做。

### 12.1 关键设计：目标必须是被右键的那一篇

`workspace.on('file-menu', (menu, file) => …)` 里的 `file` **不一定是打开着的那一篇**。
其余三个笔记级命令（收集 / 命名 / 本地化）早就接受可选的 `notePath`，
只有 `runExportNote` 还在内部写死 `getActiveFile()` —— 已补齐参数，四个命令口径统一。

命令定义随之多出一个 `runForNote(notePath)`：菜单项走它，命令面板走 `callback`，
两者最终调**同一个** `run*` 实现，差别只在"目标从哪来"；二者都包同一层 `traceCommand`，
所以从菜单进来的耗时与失败可见性与命令面板完全一致。

### 12.2 替身缺口：`Menu` 此前不存在

`addRibbonIcon` / `Menu` / `file-menu` 在替身里**全都没有实现**。也就是说，
如果直接挂菜单项，这段代码在测试里会**不可达**（覆盖审计第 ③ 级：连"改坏了会红"都没有）。
故先给替身加了 `Menu` 替身——`addItem` 真的保存 `onClick`，否则"挂上了却点了没反应"照样全绿
（与 `Setting.add*`、编辑器 `setCursor` 同一个教训）。

### 12.3 新增守卫 7 条（`tests/e2e/file-menu.test.ts`）

只对笔记出现 / canvas 也算笔记 / 附件不出现 / 每项都有点击回调 /
**目标是被右键那篇**（导出与收集各一条，且都设负对照）/ 卸载后不再追加。
逐条做过变体测试：把菜单项改回 `callback`（即 `getActiveFile()`）→ 两条目标用例转红；
去掉"只对笔记"的过滤 → 附件那条转红。

### 12.4 一个夹具教训

第一版收集用例把两篇笔记的附件写成**同一个路径**，结果 `collect` 报 `skippedShared: 1`
——索引按 basename 解析，同名会被判成"被多篇笔记共用"而按设计跳过收集。
**夹具前提必须与 expect 对得上**（这条在覆盖审计里已经栽过一次，此处是第二次）。

## 13. 配置界面文案的规范与准确（2026-10-01）

### 13.1 起因

§11 修完 4 处「承诺了却不生效」之后，又改了一批默认值（扩展扫描、笔记移动跟随、启用导出
由关改为开，见 `docs/default-settings.md`）。**改默认值几乎不会让任何用例报警**——大家都在
自己的夹具里显式设值——而设置页的说明文字是**写死的**。于是「扩展扫描」还写着
"默认关闭，以限制网络请求范围"、「笔记移动时跟随」还写着"默认关闭以免误平移"，
两句都成了假话，而全量用例**照样全绿**。这一遍就是专门去查"文案与事实是否一致"。

### 13.2 抓到的两类问题

**甲、过时表述（6 处）**——说明里自报的默认值或行为已与代码不符：

| 位置 | 原写法 | 事实 |
| --- | --- | --- |
| 扩展扫描 | 「默认关闭，以限制网络请求范围」 | 默认**开启**（且"少认一种写法"本就不该拿来当安全手段） |
| 笔记移动跟随 | 「默认关闭以免误平移」 | 默认**开启**，且只对笔记相对型目录生效 |
| 最小文件大小 | 「建议保持 0」 | 说的是默认值却没说"默认" |
| 单文件下载超时 | 「默认 30000（30秒）」 | 括号内缺空格 |
| 并发下载数 | 「超出按上限处理」 | 漏了"小于 1 按 1 处理"这半句 |
| 本地化网络 URL | 「由下方『允许本地化的类别』决定」 | 该控件早已改成「本地化 图片／视频／…」一组开关，**指向的是不存在的名字** |

**乙、凭记忆编的宿主标签（2 处）**——最坏的一类，因为它**指导用户去做、却做不成**：

- 说明写「文件与链接 → **默认附件文件夹**」，而 Obsidian zh-CN 实际叫**「附件默认存放路径」**
  （键名 `option-new-attachment-location`）——用户在设置里按这个名字找不到那一项。
- 库根提示写「改为『**与当前文件同名的文件夹**』」，真实标签是**「当前文件所在的文件夹」**
  （`option-choice-current-folder`），**且语义完全不同**：它是把附件放进**笔记所在的同一个目录**，
  不是"同名子文件夹"。照着做得到的不是文案承诺的结果。

真相来源是宿主自己的语言包：`%LOCALAPPDATA%\Programs\obsidian\resources\obsidian.asar` 的 zh-CN 段。
核对代价极低（搜 `option-` 键名即可），凭记忆写则一定出错——这条已写进 `tests/README.md` §7.4。

### 13.3 统一规范口径

- **引号**：引用命令名／开关名／设置项一律 `「」`。改前三种混用——`「」` 46 处、
  中文引号 `“”` 17 处、裸 ASCII `"` 37 处。现在 `“”` 已清零，ASCII `"` 只剩
  字面字符表 `? * " < > |` 那一处（必须保持半角，不能"顺手统一"）。
- **范围号**：统一半角 `~`（`1~16`、`16~32`、`172.16~31.x`）。改前 `2～10` 是全角、其余是半角。
- **术语**：插件自己的用语统一为**目录**（此前混用"文件夹"）；只有**引用 Obsidian 原生标签**时
  才跟着它写「文件夹」（Obsidian 的 UI 确实用"文件夹"）。另：「名称带类型类别」→「名称带类别」，
  「按类别放入子目录」的说明里"类型"→"类别"——**类别**（image/video/…）、"子类型"、"类型"
  是三件事，不能混用。

### 13.5 顺带：一个测试基建的抖动

全量跑时 `defaults.test.ts` 的「13 条命令逐条执行」用例**超时判红**，而单跑 0.8s、单文件 4/4 全绿。
原因是该用例要**串行**跑完 13 条命令，全量并发下被挤过默认的 5s。已显式给 30s。
超时是测试环境的资源竞争，不是被测行为的问题——但放任它会把这个"开箱即用"的主守卫
变成随机报红源（与 §12.4 的夹具教训同属"用例自身前提不可靠"）。

### 13.6 结论

- 全部设置项的名称与说明（43 组 `setName`/`setDesc`）**逐条**对过：控件在、消费方在、
  文案与实现一致；§11 的五形态之外，本轮补上**第六形态：文案与事实不符**。
- 文案里承诺的机制逐条兑现：`${notename}/${parent}/${parentpath}/${date}` 模板变量、
  `.`／`./assets`／裸名的语义、"全局排除目录"确实也作用于「清理空附件目录」、
  数字项全走 `bindNumber`（失焦回写实际生效值）。
- 未改的登记项见 §11.5。

## 14. 弹窗交互与提示口径：§11.5 遗留 ②③④⑤ 的修复（2026-10-02）

把 §11.5 里剩下的四条一次清掉（第 6 条 ribbon/状态栏按用户选择**不做**）。

### 14.1 ②③ 两个弹窗里的"静默失败"与"会炸的边界"

- **② 候选弹窗「以此修复」**：从前 `if (!this.picked) return;` —— 按钮看着能点，
  点下去什么也不发生、连一句提示都没有，用户只会以为功能坏了。
  改为**未选中时置灰**（`setDisabled(true)`）+ 一行"请先在上方的候选里选一个"的提示；
  选中候选后按钮点亮、提示移除。原来那句 `if (!this.picked) return;` **保留**作第二层防御
  （即使置灰态被绕过也不误改）。
- **③ `ReportModal` 空 `sections`**：原写法 `sections.every((s) => s.emptyText) ? sections[0].emptyText : …`
  —— `[].every(...)` 恒为 `true`，于是读 `[0].emptyText` 直接抛 `TypeError`。
  加一层 `length > 0 &&`。当前调用方都传满节，属"将来少传一节就炸"的隐患。

### 14.2 ④ 弹窗内的提示必须与「通知级别」「分级时长」同一口径

弹窗里的提示也是**用户可见提示**，不能自成一套数字。三条一起收口：

| 位置 | 原写法 | 现在 |
| --- | --- | --- |
| 导出报告成功 | `new Notice(msg, 3000)`（**绕过**通知级别） | `toast.summary(...)` |
| 导出报告失败 | `new Notice(msg, 5000)`（绕过级别门禁） | `toast.error(...)` |
| `runConfirmed` 回调兜底 | `new Notice(msg, 8000)` | `new Notice(msg, effectiveDuration('error', msg))` |

第三条**故意**不走 `createNoticer`：弹窗已经关了，用户必须知道"哪一步没做成"，
属"必须无条件可见"的那一类；但**时长仍走同一口径**——从前硬编码 8000，
与设置页承诺的"错误 5 秒起、消息越长越久"对不上。

为此 `ReportOptions` 新增必填的 `getNotificationLevel: () => NotificationLevel`
（由调用方注入，`modals.ts` 仍不依赖插件实例）。两个调用点（`commands.ts` 的一致性报告、
`bulk-localize.ts` 的"无可下载外链"报告）都已补传。

### 14.3 ⑤ `manifest.description` 中文化

原文 `Localize, name, audit, collect, cleanup and export attachments — all in one suite.`
改为中文。`id` / `name` **不动**——`id` 决定命令前缀 `attachment-suite:`，
改了会波及快捷键绑定、脚本调用与提示文案里的命令名。

### 14.4 先补替身缺口，否则修了也测不出来

三处替身此前是空的，直接写断言只会得到**假通过**：

- `FakeEl` 没有 `remove()`：空实现时 `querySelectorAll` 仍能找到被"移除"的元素 →
  "选中后提示应消失"照样全绿。已实现真正的从父节点摘除。
- `ButtonComponent` 没有 `setDisabled`，且 `onClick` 注册的回调**不看 disabled** →
  "置灰"这件事完全测不到。已补 `_disabled` 并在回调外再包一层判定
  （`trigger()` 走同一判定，与真实按钮一致）；顺带记录按钮文案供断言。
- `Vault.create(path, text)` 不存在（只有 `createBinary`）→ 导出报告走
  `vault.create` 一律抛 `not a function` 被 catch 成"失败"，**成功分支从来跑不到**
  （第 ③ 级不可达）。已补，并保持"同名抛错"的真实语义。

### 14.5 变体测试（逐条做过，全部按预期转红）

| 改坏什么 | 谁转红 |
| --- | --- |
| 去掉 `.setDisabled(true)` | 「刚打开时按钮是灰的」 |
| 退回空数组一行写法 | 「传空数组时不抛错」（报 `TypeError: Cannot read properties of …`） |
| 把三处时长改回字面数字 | 「静默档：导出成功不弹提示」+ **源码级**「没有把毫秒数直接写进 `Notice` 调用」+ 反向确认「用到了 `effectiveDuration`」 |
| `description` 改回英文 | 「是中文」 |

**这次变体测试暴露了一个方法论问题**：④ 最初只写了行为断言，而
`effectiveDuration('summary', 短消息)` 恰好也返回 3000 —— 把实现改回 `new Notice(msg, 3000)`
之后**行为断言照样全绿**（"硬编码恰好等于算出来的值"）。所以补了一条**源码级守卫**：
`modals.ts` 里所有 `Notice` 时长不得出现字面数字，并反向断言文件里确实用到了
`effectiveDuration`（否则第一条会因"一处都没有"而空转）。
**教训：当被测行为是"某个函数算出来的值"，而该函数对典型输入返回的正是那个魔数时，
仅有行为断言是不够的。**
