### 1.1 「自动化宿主拉不起 Obsidian」的正确解法

既有结论是"必须人工双击 `Attachment Suite/scripts/launch-obsidian-debug.cmd`"。本轮实测补两条：

- **`cmd /c start` 方式（含那个 .cmd）拉起的实例会在十几秒后被回收**：端口开过一瞬随即关闭、
  进程消失。所以"人工启动"也必须保证**父进程活着**。
- **让脚本以子进程方式拉起才可靠**：`obsidian-cdp-acceptance.mjs` 特意不用 detached，
  把 Obsidian 当作自己的子进程，脚本结束时 `taskkill /T` 收干净。实测这条路径**能跑完整个验收**（约 50 秒）。
  前提是**没有别的实例在跑**——否则新进程会被单实例逻辑吸收、永远不开调试端口。
- 因此正确的操作顺序是：**先完全退出 Obsidian**，再直接跑脚本（它会自己拉起宿主）。
  若宿主已在运行且没带调试端口，脚本会明确提示"改用人工清单模式"并退出 2。

## 3. 抓到的真实缺陷：`![[song]]` 无扩展名短名漏改 → 附件被当孤儿清理

### 3.1 现象

第一遍真实验收就报出两类悬空引用，且 `.trash/` 里出现**刚刚被改名过的附件**：

```
✗ notes/02-wiki嵌入.md 出现新断链：悬空=[wiki:notes/assets/pic.jpg]
✗ notes/14-短名无扩展名.md 出现新断链：悬空=[wiki:song]
.trash/02-wiki嵌入_image_002.jpg
.trash/14-短名无扩展名_audio_001.mp3
```

链路：附件改动 → 引用**没跟上** → 文件失去引用者 → 「清理未用附件」按"没人引用我"移入回收站
→ 笔记留下悬空引用。（回收站可恢复，但对用户而言就是"文件没了、链接坏了"。）

### 3.2 定位（`obsidian-cdp-trace.mjs` 逐命令追踪）

追踪用的是**内容指纹**而不是文件名（文件名本来就会被改名）：

```
初始            assets/mp3/song.mp3     notes/14: ![[song]]
[24] bulk-rename → assets/mp3/14-短名无扩展名_audio_001.mp3   notes/14: ![[song]]   ← 引用未变！
[58] cleanup-unused → .trash/14-短名无扩展名_audio_001.mp3    notes/14: ✗ 悬空
```

### 3.3 根因（"两层口径不一致"的第 6 次）

- 改写映射 `refMapForMoves` 只登记两个键：**完整路径** 与 **纯 basename**；
  而引用文本是**无扩展名主名** `song` → `mapping.get('song')` 查不到 → 漏改。
- **读取侧早就按主名反查**：`attachment-index` 的 `stemPaths` 把 `![[pic]]` 认作"在用"
  （那里的注释还记着"历史上正因这条口径缺失误删过附件"）。读取认、写入不认。
- 更糟的是**共享附件的"复制副本"分支自己手写键**（只写两个），所以副本刚创建就被当孤儿 ——
  这正是"同一件事两份实现、只改一份"的现场。

### 3.4 修复

- `core/link-resolver` 新增 `addRefKeys(map, from, to)`：**唯一**允许构造引用改写键的地方，
  一次登记三种写法（完整路径 / basename / 无扩展名主名；同名键不覆盖，保留先到者）。
  `refMapForMoves` 改走它。
- `features/name-formatter` 的复制分支改为复用 `addRefKeys`。

### 3.5 验证

- 单测 +3；**变体测试**：去掉主名键 → 3 条单测转红。
- 真实宿主复跑：`notes/14` 一类消失（第 2 轮起不再出现）。

## 4. 尚未解决：多轮之间的**竞态**（已定位方向）

连续 4 轮真实验收，悬空项**每轮都不一样**：

| 轮次 | 悬空项 | 问题数 |
|---|---|---|
| #1 | `notes/02`(pic.jpg) + `notes/14`(song) | 5 |
| #2 | `notes/14`(song) | 2 |
| #3 | `canvas/画布用例.canvas` 的 `file` 字段 | 12 |
| #4 | `notes/02`(`notes/assets/pic.jpg`) | 3 |

**结论：不是确定性逻辑缺陷，而是时序问题**——「批量移动/改名」与「引用改写 / 宿主索引刷新」
之间存在竞态：改动跑在了引用图上，事后重建索引就看到一个"没人引用"的文件。

方向（下一轮做）：
1. 命令结束后**不依赖宿主联动**，对本次移动集用插件自己的 `rewriteRefsInAllNotes`
   做一次全库兜底改写（`collect` / `bulk-collect` / `rename` / `bulk-rename` 路径）。
   插件已有该函数（路径修复在用），它基于**移动列表**而不是宿主缓存，正好绕开竞态。
2. 或在移动后显式等待 `metadataCache` 稳定再进入下一条命令。
3. 兜底：`cleanup-unused` 在删除前，除"当前引用图"外再核对一次"笔记文本里是否出现过该附件的
   **旧名**"（即"曾经被引用过的痕迹"），把"刚被改名但引用还没跟上"的窗口期排除掉。

> 注意：**测试替身看不到这个竞态**——替身的 `renameFile` 是同步的"全库联动改写"，
> 且没有真实的 metadataCache 延迟。这已经是第 3 次"替身比真实宿主更强"导致的盲区
> （前两次：HTML 引用、canvas `file` 字段）。真实宿主那一遍验收因此**不可省略**。

## 6. 追加：接上宿主控制台采集，第一轮就抓到"失败原因从不落日志"

### 6.1 工具：控制台采集（`scripts/obsidian-cdp-trace.mjs`）

排查"为什么会失败"时，磁盘状态只能告诉你"结果坏了"，**控制台才告诉你"哪一步抛了什么"**。
追踪脚本现在采集三条 CDP 通道，外加一条 CDP 看不到的：

| 通道 | 拿到什么 |
|---|---|
| `Runtime.consoleAPICalled` | 插件 `logger.*` 的实际落点（`[IAP]` 前缀）、Obsidian 本体与第三方输出 |
| `Runtime.exceptionThrown` | 未捕获异常、未处理的 Promise reject（异步链路最容易静默失败处） |
| `Log.entryAdded` | 浏览器级错误（资源加载失败等，不会走 console） |
| `.notice` 元素 DOM 观察器 | **插件对用户的失败提示走 Notice 而不是 console** —— 不观察 DOM，就看不到"命令报错了"这件事本身 |

用法：`--console-only`（只看日志）、`--filter "失败|EXCEPTION|NOTICE"`（只看关注的）。
完整时间线落 `for-test/acceptance-reports/obsidian-console-<时间戳>.log`。

> 局限（已知）：命令是异步的，脚本只等固定时长就切窗口，某条命令末尾的日志可能落到**下一步**的
> 窗口里。跨步骤定位时以日志内容为准，不要以它落在哪一步为准。

### 6.2 抓到的缺陷：失败明细被构造出来后直接丢弃

第一轮就报出：`收集当前笔记附件` 显示「失败 2 项」，提示还写着
「详情见开发者控制台（Ctrl/Cmd+Shift+I）」，**而控制台里一条原因也没有**。

排查全部错误计数点，同一形态共 6 处：

| # | 位置 | 丢失方式 |
|---|---|---|
| 1 | `collect.ts` | `out.errors` 只取 `.length` |
| 2 | `bulk-collect.ts` | `errors += out.errors.length`，明细丢弃 |
| 3 | `consistency.ts` | 同上 |
| 4 | `name-formatter.ts` | `out.errors` 丢弃；`copyFileTo` 的 `catch { return false }` 把原因也吞了；`notify=false`（全库命名逐篇调用）时整段明细被跳过 |
| 5 | `unused-cleaner.performDelete` | `catch { errors++ }` —— 破坏性命令的删除失败原因丢失 |
| 6 | `empty-folder-cleaner` | 同上 |

另有 `broken-link.ts` 的"笔记不存在"分支只计数不记录。

**修复**：`reportFailures(toast, count, what, details?)` 增明细参数并逐条 `logger.error`；
新增 `logFailures` 供刻意逐篇静默的批量流程使用（逐篇静默不应连日志一起静默）；
`details.length < count` 时补一条「其中 N 项没有可用明细（原因在产生处被丢弃）」，把缺口显式暴露。

**这是「设置项/提示承诺了却不生效」的又一形态**：文案承诺"详情见控制台"，代码从不写控制台。
判据同样是那句——**能不能指出"这句承诺由哪段代码兑现"**。

### 6.3 修好日志后读出的真实失败原因

```
[IAP] 收集失败：assets/png/01-正文图片_image_001.png → notes/assets/01-正文图片_image_001.png：
      改名失败 …: ENOENT: no such file or directory, rename '…\assets\png\01-正文图片_image_001.png' -> …
```

`from` 是「**改名后的文件名** + **改名前的目录**」——说明计划用的快照与磁盘不一致：
宿主文件列表的更新相对插件快照是滞后的。这与第 4 节登记的那个竞态**同源**，
只是它并非随机：命令背靠背连发（追踪/验收脚本的固定节奏）就会稳定出现，交互使用时被人手延迟掩盖。

> 结论：**这不是"计划算错"，而是"计划所依赖的宿主状态已经过期"**。
> 方向仍是第 4 节那条：命令结束后不依赖宿主联动，用插件自己的 `rewriteRefsInAllNotes`
> （基于移动列表）做全库兜底；并在执行前对 `from` 做一次存在性核对，缺失时**按内容重解析**
> 而非直接报错。

## 7. 诊断模式可达化，并据此定位到"移动前不建目标目录"（提交 `9c8b9fd`）

### 7.1 决策：命令式诊断，而不是设置项

`setLogLevel` 长期零调用、级别硬编码在 `info` → `logger.debug` 的 7 处调用**永远打不出来**。
这是「承诺了却不生效」的第 5 种形态（接口存在，却没有任何路径让它生效）。修法选了**命令**：

| | 命令式诊断（采用） | 设置项 |
|---|---|---|
| 语义匹配 | 是"此刻要复现一个问题"的**临时状态**，重启即复位（安全阀） | 长期偏好；持久化会让人忘了它开着，而 debug 日志含库内文件路径 |
| 可验证性 | 人工与 CDP 自动化走**同一条路径**，这条路径能被用例钉死 | 也能测，但解决不了"排查时怎么打开它"这个动作问题 |
| 风险 | 无新增设置面 | 设置页每加一项都是一条必须兑现的承诺（已因"承诺了却不生效"栽过 5 次） |

关键前提：**开关必须真的有东西可看**，否则它自己就是第 6 次同类缺陷。为此把诊断出口补到该补的地方——
索引（`AttachmentIndex`）与移动引擎（`SafeMoveEngine`）在 `core` 里不能 import `logger`，
改为**构造时注入**，由 `main.ts` 接到 `logger.debug`；各命令补计划明细。

### 7.2 定位：ENOENT 的真身不是"源不存在"

真实宿主上稳定复现：`收集当前笔记附件` → `收集完成：移动 0，失败 2`，
错误 `改名失败 assets/png/01-…png → notes/assets/01-…png: ENOENT`。

新加的诊断直接给出反证：

```
[移动] 移动：assets/png/01-正文图片_image_001.png（源存在：是）   ← 源文件好端端在磁盘上
[移动] 移动：assets/dup/01-正文图片_image_002.png（源存在：是）
```

于是问题不在源。**是我一直误读了错误文本**：Node 的 `fs.rename` 在**目标父目录缺失**时同样抛
ENOENT，而消息里会一并打印源与目标。

**根因**：`ObsidianFileOps.rename` 直接调 `fileManager.renameFile`，它**不创建**目标目录。
于是任何"笔记目录下还没有附件目录"的库，第一次收集/命名必然整批失败——实测 `notes/assets/`
**从未被创建过**（历轮"收集完成：移动 0"全是失败）。本地化与笔记重定位早就各自 `ensureFolder` 了，
只有"移动"这条公共出口漏了。

### 7.3 为什么 harness 全绿

`tests/e2e` 的替身 `renameFile` 里有 `mkdirSync(dirname(dst), { recursive: true })`
——**替身比真实宿主更强**，于是"目标目录不存在"这类失败在 E2E 里永远看不到。
已把替身降级到与宿主一致（缺目录即抛 ENOENT），并做变体测试：回退 `ensureFolder` →
`real-suite` 立即转红。

> 这是第 4 次"替身保真度"造成的盲区（前三次：HTML 引用、canvas `file` 字段、metadataCache 延迟）。
> 规律很清楚：**替身每多兜一层，就有一类真实缺陷在 CI 里隐身。**

### 7.4 结论：此前的"竞态"有一部分是本缺陷

修复后完整验收：**82 条用例 × 13 命令 → 问题 0，第 3 轮收敛**（此前"5 条"→"2 条"→"每轮悬空项都不同"）。
回看那个"每轮悬空项都不一样"的现象，一部分正是本缺陷的表现：目标目录是否已存在，
取决于前面命令是否恰好建过它 → 表现为随机。**"看起来像竞态"不等于就是竞态**，
用 `--step-delay 2500` 放慢节奏后失败依旧，就已经排除了节奏因素。

## 8. 追加：诊断日志同时做成设置项（提交 `fe32e4b`）

### 8.1 结论：**两者都要，但必须是同一个状态**

命令解决"就在排查现场、临时开一下"，设置项解决"想让它一直开着"。二者不是替代关系，
但**绝不能各写一套**——本仓库已因"同一件事两份实现、后来只改一份"栽过 6 次。
故只留一个入口：

```
设置页开关  ─┐
             ├─→ plugin.setDebugLogging(next)  →  改设置 → 立即生效 → 落盘
命令         ─┘
```

配套的三条约束（都是本仓库"承诺了却不生效"的既有形态）：
1. **读进来就得生效**：`loadSettings()` 里调 `applyLogLevel()`，否则配置只是个字段；
2. **先生效再落盘**：落盘失败也不会出现"界面显示已开启、日志级别其实没变"；
3. **命令以设置（而非 logger 当前级别）为准**：否则设置页会显示"关"而实际是"开"。

### 8.2 顺带抓出的静默丢弃：迁移白名单漏键

`settings-migration.normalizeFields` 里有一份**手写的"已知顶层键"白名单**，它与 `PluginSettings`
是同一件事的两份实现。本次先加了 `debugLogging` 字段、**漏了白名单** —— 后果是配置在**每次读取时
被静默丢弃**，表现为"设置页改好、重启后自己变回默认"，且没有任何报错。

被发现纯属侥幸（新写的"重载后仍生效"用例报红）。已补白名单，并加了一条通用守卫：

> `DEFAULT_SETTINGS` 的**每个顶层键**逐个做往返断言（布尔翻转 / 数字 +1 / 字符串加后缀 /
> 嵌套区翻一个布尔键）。漏键即转红。

变体测试确认该守卫有效（去掉 `debugLogging` 立即转红，并指名是哪个键）。

### 8.3 验证

- 变体测试三次全红：设置页开关只改字段 / 命令只改级别 / 迁移白名单漏键。
- 真实宿主：只写一份 `{ "debugLogging": true }` 的 `data.json`（顺带验证旧配置迁移），
  **不传 `--debug`** 启动 → 控制台出现 `[索引] 索引重建完成：文件 71，受管附件 20…`，
  证明"落盘 → 读取 → 迁移 → 生效"整条链路通。
- 全量：**32 文件 / 415 用例全部通过**；`typecheck` 通过。

### 8.4 一个可复用的教训

**"手写白名单"是本仓库最容易被漏的一份实现**：`normalizeFields` 的已知键、架构守卫的
`ALLOWED_CROSS_FEATURE`、`GUARDED_CONTENT`——它们都与另一处定义构成隐性重复。
每新增一个字段/依赖/保护对象，都要问一句：**"还有哪份清单需要同步？"**
能写成"遍历源定义、逐个断言"的守卫，就不要靠记忆去补清单。

## 9. 启动哨兵：把"打开库不会静默批量改写"变成可验证的事实（2026-09-29）

### 9.1 为什么这件事最重要

插件唯一一条**不经用户同意就批量改写整库**的路径，是自动处理：
`runAutoProcess` 内部调 `runRenameNote(..., confirm=false, ..., notify=false)` —— **不弹确认框**。
而它的入口是"启动期 Obsidian 对全库笔记批量触发 `metadataCache.changed`"。
一旦这些事件被当成"用户编辑了这篇笔记"，用户**只是打开了 Obsidian**，整个库的附件就会被改名、
搬进各笔记的归属目录，事后才发现。

此前这道防线**在测试里根本不可达**：抑制窗口写成 `STARTUP_SUPPRESS_MS = isTestEnv ? 0 : 1500`，
测试环境恒为 0 → 那行判断在任何测试里一次都不执行，改坏了也不会红。

### 9.2 实测：启动期的批量事件是真实存在的

带 automation 打开验收库（48 篇笔记），插件诊断（`getAutomationDiagnostics()`）给出的实测值：

| 计数 | 值 | 含义 |
|---|---|---|
| `suppressedNotSettled` | **48~49** | 就绪**前**被挡下的 changed（≈ 每篇一个） |
| `suppressedQuiet` | **46** | 就绪**之后**的余震窗口内被挡下的 |
| `settleSource` | `metadataCache.resolved` | 就绪信号来自宿主事件，不是兜底超时 |
| `readyAt → settledAt` | **70ms** | 插件随宿主启动加载，索引在它之后才完成 |
| 打开的库被改写 | **0 篇** | —— |

两点结论：① 启动期真有约 95 次 `changed`；② **余震窗口是必需的**——
有 46 次发生在 `resolved` 之后，只靠"就绪事件"一个信号会漏掉它们。

### 9.3 变体实验：这道哨兵不是空洞的

每次都是重新 seed 的干净库、automation 在启动时即开启、全程**不做任何操作**：

| 变体 | 笔记改写 | 哨兵附件 | 护栏拒绝 | 判读 |
|---|---|---|---|---|
| **完整实现** | **0 篇** | 完好 | 0 次 | 打开库没有改写任何东西 |
| 只关就绪门 | 0 篇 | 完好 | **1 次** | 批量事件**确实会漏进轮询**；护栏挡住了 |
| 就绪门 + 护栏都关 | **31 篇** | **已消失** | 0 次 | **缺陷真实复现** |

第三行就是那个"看似轻、实则严重"的后果——**仅"打开库"就改写了 31 篇笔记、附件被改名搬走**。
第二行说明两道防线各有职责：护栏能保住库不被改写，但用户会每次开库都收到一条
"检测到 46 篇同时待处理，已跳过"的告警；就绪门才是让这件事压根不发生的那一层。

### 9.4 落地

- 新增 `--startup-check` 阶段：启动前记全库笔记内容基线 + 放一个"哨兵附件"（名字不合规，
  一被处理就会改名/搬走），启动后不触碰库、等过"就绪兜底 + 余震窗口 + 两轮轮询"，逐篇比对。
- 实现见 `src/features/automation-core.ts`（纯决策逻辑）+ `src/main.ts`；
  判据、兜底与护栏阈值都在该模块的注释里。
- 这轮还顺带补了替身的生命周期保真度：`Plugin.register` 此前**不存在**、`registerEvent` 是**空实现**、
  `on()` 不返回 EventRef —— 于是"插件有没有把事件/定时器交给宿主托管"在 CI 里完全不可验证。
  现已支持并加了"卸载清理后不再触发"的用例。
- 最终验收：`问题 0、第 3 轮收敛`；启动哨兵 `0 篇改写 / 哨兵完好`，自动化阶段**已生效**
  （`assets/AutomationProbe_image_001.png`，1056ms）作为正对照。

### 10.2 抓到的缺陷：追踪脚本不启动本地 HTTP 服务

**现象**：修复前**每一次**追踪的控制台里都有
`[IAP] 下载失败：http://127.0.0.1:45999/…（net::ERR_CONNECTION_REFUSED）`（4 条），
外加 7 条 `[log.error] Failed to load resource: net::ERR_CONNECTION_REFUSED`。

**根因**：验收脚本自带本地 HTTP 服务（外链用例的**被测目标**），**追踪脚本没有**。后果有两层——

1. 追踪结果里混入 4 条**工具自己造的假失败**：这份控制台正是用来"区分真失败与噪声"的，
   它自己制造噪声等于把排查带偏；
2. 外链本地化那条链路在追踪里**根本跑不到**，"到底是哪一步把附件写坏的"无从定位。

**修法**：抽成 `scripts/lib/acceptance-http-server.mjs`，两个 CDP 脚本共用一份实现；
追踪侧端口被占时**只告警不中断**（属环境问题，不是插件缺陷）。配套守卫见 10.3。

修复前后（同一条命令）：

| | `ERR_CONNECTION_REFUSED` | 外链下载 |
|---|---|---|
| 修复前 | **7 条** | 全部失败 |
| 修复后 | **0 条** | `全库本地化完成：下载 14，跳过 3，失败 0` |

修复后仍留在控制台里的 3 条 warning **是预期的负向用例**，不是缺陷：
`跳过非受管附件类型（.txt）不落盘`、`跳过网页文档（不落存 HTML）`、
`下载失败：…:1/blocked.png（net::ERR_UNSAFE_PORT）`。

### 10.3 方法论：新守卫第一版是"恒真的"，靠变体测试抓出来

新守卫初版对**原文**做 `toContain('acceptance-http-server.mjs')`。按规矩做变体测试
（把导入整行删掉）——**居然照样全绿**：因为那个串在**说明性注释**里也出现，
注释把断言"喂饱"了。改成**先剥注释再断言**之后才真正转红。

→ **`toContain` 型守卫必须先剥注释**，否则就落进"有断言但恒真"（第 ① 级未覆盖）——
它比"没断言"更危险，因为看起来是被覆盖的。这条与 `acceptance-tooling.test.ts` 里
既有的 `codeOnly` 写法是同一个道理，现在两侧统一了。

### 10.4 环境坑（同一个坑第二次踩到，且发现了第二个）

- `python -c "…"` 形式的补丁脚本会**执行两次**：第一次改成功，第二次因锚点已失效而
  抛 `AssertionError`（输出里看到报错、文件其实已改好）。**所以不能用 `assert` 当幂等保护**，
  要写成"先判断再改"。本次就是这样：以为失败了，实际退化已生效。
- 本次新发现：`cat > file << 'EOF'` 形式的 heredoc **同样会执行两次**——守卫代码块被追加了两遍，
  用例数从预期的 7 变成 10 才暴露出来。
- Git Bash 下 `/tmp` 不可靠（写进去的文件随后读不到）：临时文件放**项目内**更稳。
